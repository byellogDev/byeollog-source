# 2026-09-05 긴급 배포 영향 점검

## 범위와 결론

대상: 현재 1.0.0.26 소스에 포함된 회차 선택/로컬 백업, 24~26 긴급 수정(표시 revision, 부분 이미지 복구, null 좌표/버전), 관련 편집 API와 게이트웨이 순서 처리.

사용자가 실제 오류 해결을 확인한 뒤 수행한 후속 점검이다. 운영 코드·DB·설치판·OBS는 변경하지 않았다. 격리 진단용 파일과 테스트 진입점만 추가했다. 과거 실방송 전 보고서의 통과 여부를 이번 릴리스의 실환경 검증으로 재사용하지 않았다.

현재 모든 사용자에게 지속적인 부하가 늘어난다는 증거는 없지만, 장애 시 복구/부하 경계와 업데이트 검증에 보완이 필요하다. 아래 테스트는 실제 운영 트래픽 측정이나 테스트 스트리머 PC 장시간 시험이 아니다.

## 발견 사항

### 1. 높은 우선순위: 이미지 본문 정지 시 후속 카드도 대기

- 위치: `WallpaperOverlayState.cs`의 `ApplyAsync`/`CacheRemoteImageAsync`, `VNextDevelopmentClient.cs`의 `DownloadAuthenticatedWallpaperImageAsync`.
- 이미지 요청은 `ResponseHeadersRead`로 헤더를 받은 후 본문 스트림을 별도로 읽는다. 본문 전체를 제한하는 전용 취소 시한은 없고 호출자의 취소 토큰을 사용한다.
- 카드 이미지를 순서대로 기다린 뒤 상태를 한 번에 반영한다. 따라서 이미지 한 개가 끝나지 않으면 정상 카드도 대기하고, `VNextLocalAgent`의 적용 gate가 유지되어 후속 스냅샷 반영도 지연될 수 있다.
- 격리 재현: 헤더는 즉시 반환하고 첫 이미지 본문만 정지시켰다. 16초 후에도 적용 작업이 미완료, 시작된 이미지 요청은 1개, 표시 카드는 0개였다. 정지를 해제하자 2개 카드가 표시됐다.
- 신규로 만든 결함이라고 단정하지 않는다. 기존 순차 다운로드 경계가 이번 부분 복구 패치로도 해결되지 않은 것이다.
- 권고: 본문 전체를 포함하는 다운로드 시한, 정상/텍스트 카드 선반영, 제한된 다운로드 동시성 및 최신 스냅샷 우선 처리. 후원 알림 수신을 이미지 복구 대기와 분리해야 한다.

### 2. 중간 우선순위: 영구 이미지 실패의 반복 비용

- 위치: `VNextLocalAgent.ScheduleWallpaperRetry`, `WallpaperOverlayState.ApplyAsync`, `CollectorStorage.Log`.
- 이미지 실패가 남으면 서버 cursor를 완료 처리하지 않고 5초 타이머로 다시 요청한다. 타이머 중복과 동시 fetch는 제한되지만 지수 backoff/영구 실패 분리는 없다. 새 Realtime 신호는 별도로 즉시 요청할 수 있으므로 5초가 전체 요청률의 엄밀한 상한은 아니다.
- 정상 이미지 캐시는 재사용하지만 스냅샷 재조회와 실패 이미지 요청은 반복될 수 있다.
- 동일 실패 스냅샷을 3회 적용한 모의 시험: HTTP 4회(정상 이미지 1회 + 실패 이미지 3회), 서로 다른 displayRevision 3개, 오류 로그 3개, 완료 cursor 0 유지.
- 실패 내용이 동일해도 상태 파일을 저장하고 displayRevision을 바꾸므로 OBS 갱신과 편집기 변경 알림도 발생한다. 로그는 append 방식이며 크기 회전 정책이 없다.
- 권고: 이미지별 backoff/영구 실패 분류, 같은 실패 상태의 저장·렌더·로그 생략. 신규 후원 즉시 수신 경로에는 backoff를 적용하지 않는다.

### 3. 중간 우선순위: 권한 없는 요청이 다른 작업공간 한도 소진 가능

- 위치: `api/login.js`의 `handleAgentWallpaperControl`.
- bearer가 비어 있지 않고 workspace UUID 문법이 맞으면, 실제 인증/소속 확인 전에 작업공간별 DB rate-limit 카운터를 차감한다.
- 대상 workspace ID를 아는 경우 잘못된 bearer로도 해당 작업공간의 회차 선택 한도에 영향을 줄 수 있다. 데이터 읽기/쓰기를 허용하는 결함은 아니며 가용성 문제다.
- 네트워크 없이 실제 핸들러 함수와 모의 인증/카운터로 재현: 잘못된 인증 120회는 401, 그 뒤 정상 인증 요청은 인증 단계 전 429, 실제 쓰기는 0회.
- 권고: 인증 전에는 별도 IP 등의 방어 한도, 인증 후에는 검증된 사용자/작업공간 한도를 사용한다. 현재 제한을 단순 삭제하지 않는다.

### 4. 중간 우선순위: 업데이트 실패 가시성과 배포 검증

- 24/25 실제 배포 EXE 사전검사는 각각 기대 버전으로 실행 시 exit 3, 내부의 23을 기대하면 exit 0이었다. 26은 기대 버전 26으로 exit 0이었다(앞선 이번 대화의 실제 배포본 검사).
- 버전 원천 통합으로 26은 고쳤지만, `--update-preflight <배포 버전>` 실행을 패키징/배포의 필수 차단 조건으로 고정하지 않으면 유사한 결함이 재발할 수 있다. 현재 추가된 소스 계약 검사는 실제 배포 EXE 검사를 대체하지 못한다.
- 업데이트 실패 시 `failed_kept_current`/오류 코드를 파일에 기록하고 구버전으로 계속 시작한다. 기존 실행 보존은 필요하지만 사용자에게 최신 적용 여부가 명확히 드러나지 않는다.
- 권고: 서명된 카탈로그/실제 EXE 사전검사/구버전에서 업데이트 경로를 릴리스 게이트로 묶고, 실패와 실제 실행 버전을 UI에 구분해 안내한다. 기존 정상 버전 유지와 서명 검증은 유지한다.

## 통과한 검증

- .NET 전체: 761 assertions 통과. 종료 기능 관련 검사도 포함되므로 이 숫자가 현재 제품 전체 검증을 의미하지 않는다.
- 부분 이미지 실패 후 정상 카드 보존, 중복 이미지 다운로드 방지, 같은 revision 재복구, 재시작 후 미완료 이미지 복구, 오래된 스냅샷 차단, 로컬 배치 보존, 취소 시 기존 화면 유지.
- 실제 격리 localhost HTTP 및 실제 렌더 함수: 로컬 x=100→500 변경 시 서버 revision 9 유지/렌더 1회; HTTP 503, 렌더 예외, 상태 요청 정지 후 복구.
- 로컬 보안: 직접/동일 출처 요청 200, 교차 사이트/불투명 출처 요청 403. 이미지 허용 호스트·크기·해시 검증은 유지돼 있다.
- 백업 모의 시험: 로컬 조회 240회에 최초 서버 조회 1회, 편집 20회에 백업 1회, 지연 백업 중 편집/후원 비차단.
- 서버 선택 검사 57개 통과(업데이트 피드/릴리스 저장소, 후원 분류, outbox/순서, 풍벽지 계약). 추가 선택/저장/캐시/인증·보안 검사 28개 통과.
- Agent Node 계약 11개 통과. 신버전/heartbeat 원천, overlay/realtime 경계를 포함한다.
- 게이트웨이 동일 작업공간 순서, 다른 작업공간 비차단, 실패 후 큐 회복 및 shutdown drain 검사 통과. 중앙 서버에 실부하/장애를 주입하지 않았다.

## 재현 명령

Agent 폴더:

```powershell
dotnet run --project AgentStoreTests/AgentStoreTests.csproj -- --audit-emergency-impact
node tools/Diagnose-WallpaperRender.mjs
```

서버 폴더:

```powershell
node tools/Audit-WallpaperControlQuota.mjs
```

첫 번째와 세 번째 명령은 현재 위험을 관찰하는 진단이며, 성공 종료를 무결함 판정으로 해석하면 안 된다. 모든 데이터/인증/이미지 응답은 격리 fixture다.

## 미검증 및 다음 조치

- 실제 테스트 스트리머 PC/OBS의 장시간 메모리·CPU, 운영 실패 이미지율/서버 요청량은 이번에 측정하지 않았다.
- 다수 동시 사용자 용량, 여러 PC가 같은 작업공간 배치를 동시에 변경하는 실환경은 별도 시험이 필요하다.
- 이번 점검에서는 수정·배포를 하지 않았다. 우선 1번을 해결한 뒤 2~4번을 분리된 회귀 시험과 함께 적용하는 것을 권고한다.
