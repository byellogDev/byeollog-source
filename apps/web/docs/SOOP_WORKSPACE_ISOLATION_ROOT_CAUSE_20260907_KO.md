# SOOP 워크스페이스 교차 수집 원인 및 격리 조치 보고서

작성일: 2026-09-07

## 결론

교차 수집의 직접 원인은 여러 SOOP ChatSDK 인스턴스를 하나의 Chromium 브라우저 컨텍스트에 함께 배치한 설계와, SDK가 실제로 연결한 방송국 ID를 서버가 검증하지 않은 설계가 동시에 존재한 것입니다. 내부 세션 ID는 SDK 콜백이 발생한 이후의 전달 대상을 구분할 뿐, SDK 내부의 페이지 전역 상태와 저장소를 격리하지 못합니다.

시그풍 이미지는 등록 자산 테이블의 무조건적인 타 계정 조회로 넘어간 것이 아닙니다. 과거 쿼리는 `signature.workspace_id = p_workspace_id`로 제한되어 있었습니다. 그러나 계정 A 방송의 이벤트 자체가 계정 B 워크스페이스로 잘못 귀속되면서, 그 이벤트에 포함된 방송국 전용 `imageUrl`과 잘못된 후원 카드가 계정 B 풍벽지 경로에 들어갈 수 있었습니다. 당시 기록 정리 후 원본 방 ID가 보존되지 않아 문제 화면의 URL 출처를 사후 100% 복원할 수는 없지만, 현재 자산 메타데이터상 계정 B에는 문제 화면의 해당 금액 등록 자산이 없고 계정 A에만 있으므로 이 경로가 코드와 데이터에 부합합니다.

## 왜 같은 SDK 채팅 컨텍스트를 사용했는가

2026-09-02 체크포인트의 운영 기본값은 Chromium 프로세스 하나와 샤드당 16개 세션이었습니다. 당시 문서에는 추측 불가능한 세션 ID와 서버 세션 맵으로 워크스페이스가 격리된다고 명시되어 있었습니다. 이는 성능 최적화를 위해 브라우저 자원을 공유하면서도 애플리케이션 레벨 라우팅이 격리를 보장한다는 잘못된 전제였습니다.

누락된 경계는 다음과 같습니다.

1. 세션별 독립 BrowserContext가 없었습니다.
2. `handleReady`에서 얻은 `bjId`와 `chatNumber`를 모든 이벤트에 붙이지 않았습니다.
3. 서버가 요청 본문의 `workspaceId`를 신뢰했습니다.
4. 워크스페이스의 정식 SOOP ID와 SDK의 실제 `bjId`를 비교하지 않았습니다.
5. 동일 공급자 이벤트가 서로 다른 워크스페이스에 저장되는 것을 막는 전역 고유 제약이 없었습니다.
6. 기존 시험은 샤드 용량과 콜백 분배를 확인했을 뿐, 두 실제 SOOP 계정의 SDK 방 정체성을 동시에 검증하지 않았습니다.

## 적용한 격리 조치

- 워크스페이스마다 독립 Chromium BrowserContext를 생성하고 운영 세션 밀도를 1로 고정했습니다.
- SDK의 실제 `getRoomInfo()` 결과를 준비·이벤트·heartbeat마다 전달합니다.
- 서버가 워크스페이스, 정식 SOOP ID, 게이트웨이 인스턴스, 만료 시각을 서명한 단기 lease를 발급합니다.
- 게이트웨이와 서버가 실제 `bjId` 및 `chatNumber`를 lease와 대조하고, 불일치·누락 이벤트를 저장 전에 거부합니다.
- 이벤트 fingerprint의 전역 소유권을 DB에서 원자적으로 선점하며 다른 워크스페이스의 재사용을 충돌 감사 테이블로 격리합니다.
- 후원, 룰렛 결과, 풍벽지 이미지 선택 단계가 각각 DB에서 워크스페이스·방·이벤트 소유권을 다시 검증합니다.
- 풍벽지 타일과 룰렛 결과가 다른 워크스페이스의 후원 행을 참조하지 못하도록 복합 외래 키를 추가했습니다.
- 정식 소유권 정보가 없는 이전 후원·룰렛 RPC는 새 API와 게이트웨이 배포 뒤 별도 마이그레이션에서 서비스 권한을 회수합니다.

## 검증 결과

- 전체 자동 시험: 606 통과, 실패 0.
- 두 워크스페이스가 동일 이벤트 fingerprint를 동시에 제출하는 시험: 최초 워크스페이스만 저장되고 두 번째 워크스페이스는 409 충돌로 격리됨.
- 다른 `bjId`, 다른 `chatNumber`, 다른 게이트웨이 인스턴스, 변조·만료 lease: 모두 저장 전에 거부됨.
- 2026-09-07 운영 데이터 재감사: 결과-후원 교차 연결 0, 풍벽지-후원 교차 연결 0, 공급자 이벤트 ID의 다중 워크스페이스 중복 0, 후원 내역 키 중복 0.

## 운영 반영 전 남은 검증

코드와 격리 시험은 완료됐지만 아직 운영 배포 완료를 의미하지 않습니다. 실제 두 방송 계정을 동시에 연결한 SOOP SDK → 서버 → Agent → OBS 검증은 운영 반영 뒤 수행해야 합니다. 배포 순서는 DB의 호환 마이그레이션, Vercel API, NCP 게이트웨이, 실제 방 정체성 확인, 이전 RPC 권한 회수 순이어야 하며 중간 버전 혼용 동안에는 수집을 잠시 멈추는 것이 안전합니다.
