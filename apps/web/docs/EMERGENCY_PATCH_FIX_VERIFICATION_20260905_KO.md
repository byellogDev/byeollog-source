## 회귀 검증

- .NET 전체 789 assertions 통과, 긴급 복구 전용 70 assertions 통과. 전체 개수에는 종료된 기능의 기존 검사도 포함되므로 실제 제품의 전수 검증으로 해석하지 않는다.
- Agent Node 계약 검사: 211/211 통과.
- 서버 Node 검사: 437/437 통과.
- 실제 격리 localhost HTTP + 제공되는 오버레이 갱신 함수: 로컬 x=100→500, 서버 revision 9 유지, 갱신 1회. HTTP 503/렌더 예외/요청 정지 후 복구 통과. 교차 출처 접근 403 유지.
- 기존 백업 시험: 로컬 조회 240회에 초기 서버 조회 1회, 로컬 편집 20회에 백업 1회. 지연 백업이 편집/후원 반영을 막지 않음.
- 부분 이미지 복구, 중복 이미지 재사용, 재시작, 오래된 응답, 로컬 배치 보존, 취소 검사를 함께 통과했다.
- 브라우저 검증 스킬로 분리된 로컬 HTML을 413×560 화면에서 확인했다. 업데이트 경고 하단 약453px, 편집 버튼 상단 약470px로 겹침 없음. JavaScript 오류 없음. 고객의 실제 Agent/OBS를 실행하거나 조작한 검사는 아니다.
- 일부 기존 소스 계약 검사가 과거 23 버전/순차 다운로드 구현을 요구해, 실제 단일 버전 원천/새 경계 검사로 수정했다. 검사 삭제나 실패 무시는 하지 않았다. 문서 개인정보 검사에 걸린 기존 점검 문서의 실제 스트리머 표기도 일반 명칭으로 치환했다.

## 부하 변화와 남은 위험

- 정상 Realtime 알림/후원 수신 주기를 늦추지 않았다. 실패 이미지의 재시도 지연은 새 이미지 키와 새로운 후원 신호에 적용하지 않는다.
- 원격 편집 API 요청에는 인증 보호용 rate-limit DB RPC가 **1회 추가**된다. 로컬 배치 조작/OBS 상태 폴링 자체에는 추가 서버 요청이 없다. 보안 보강 비용이 전혀 없다고 주장하지 않는다.
- 캐시가 없는 시작 시 최대 4개 이미지 요청을 병렬 처리하므로 순차 방식보다 순간 네트워크/메모리 사용이 늘 수 있다. 제한 없는 병렬화는 아니며, 이미지 크기/호스트/해시 제한은 유지한다. 실제 고객 PC의 최대 이미지 크기·저속 회선에서 피크 메모리/시간은 추가 확인 대상이다.
- 본문이 15초 내 완료되지 않는 이미지는 부분 표시 후 재시도된다. 실패 이미지가 나중에 복구되는 시간은 최대 5분 재시도 간격의 영향을 받을 수 있다. 새 후원 인입과 정상 카드 반영은 별도다.
- 실제 운영 요청량, 고객 PC/OBS 장시간 안정성, 여러 PC 동시 편집은 이번 격리 시험으로 증명하지 않았다. 구조 변경으로 인한 무회귀를 보장한다는 뜻이 아니다.
