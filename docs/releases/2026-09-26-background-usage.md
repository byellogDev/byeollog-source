# 2026.09.26-background-usage · 불필요한 반복 요청 축소

## 상태와 범위

- 상태: 백업 워커, 목록 메타데이터 RPC, NCP 반복 작업 운영 반영.
- 확인 시각: 2026-09-26 09:33 KST.
- 웹·관리자·수집·공개 조회 런타임은 재배포하지 않았다. 수집 컨테이너, heartbeat, 연결 확인, API 중계와 권한 경계도 유지했다.
- 이전 운영 기준: [리포트 버튼 표시 수정](2026-09-26-report-button-visibility.md). 이번 변경은 해당 화면과 독립적이다.

## 목적과 변경 전 문제

12시간 운영 기록에서 업보 재시도 697회 중 695회는 가져온 작업이 없었다. 백업 보존기간 정리는 188개 성공·5개 실패 후 재실행하면서 193개 전체를 다시 검사했다. 일일 독립 백업은 별도로 정상 완료되어 있었다. 반복 요청 절감과 자동 백업 제거는 별개다.

이 관측은 해당 구간의 중복 작업을 증명한다. 30일 전체 CPU 사용량의 원인이 모두 이 두 작업이라는 뜻은 아니다. 기존 HTTP 500의 근본 원인도 이번 변경으로 해결됐다고 판단하지 않는다.

## 변경 내용과 소유 구성요소

- NCP 업보 재처리: 기존 분당 타이머·자격증명을 유지하고 빈 응답이 연속되면 실제 API 요청 간격을 60→120→240→300초로 늘린다. 작업이 발견되면 60초로 복귀한다. 오류·해석 불가능 응답은 대기 상태를 지워 다음 분에 재시도한다. 타이머 실행 자체는 계속된다.
- 백업 워커: 내용 변경 없이 검사를 완료했을 때만 원본 수정 시각과 다음 검토 시각을 반환한다. 다음 검토는 남은 풍벽지 기록의 7일 만료 시각과 24시간 중 이른 시각이다.
- NCP 보존기간 정리: 원본 버전·검토 기한·로컬 복사본 해시가 모두 같을 때만 파일 처리 요청을 생략한다. 실패 파일, 변경된 원본, 새 복사본, 만료된 검토 기록은 다시 처리한다. 성공 결과를 파일별로 저장해 부분 실패 재실행을 지원한다.
- DB: 기존 목록 RPC에 `updated_at`만 추가했다. 반환 형식과 기존 실행 권한을 유지했다.

## 검증

| 항목 | 방법 | 결과 | 확인하지 못한 범위 |
| --- | --- | --- | --- |
| 자동 검사 | 전체 Node 검사 | 797건 통과 | 실제 장기 운영 절감률 |
| NCP 검사 | Python unittest, 로컬 및 Linux 후보 | 각각 10건 통과, 부분 실패·재개·원본 변경·해시 변화·오류 복귀 포함 | 장기간 시스템 시계 변화 |
| 워커 소스 | 후보와 로컬/직전 배포 파일 비교 | 16개 소스 일치, 의도한 2개 파일만 변경 | 없음 |
| 권한 | 비인증 후보 호출, DB 함수 권한 대조 | 비인증 401, 기존 권한 유지 | 모든 보안 경로 재검증은 이번 범위 밖 |
| 실제 목록 조회 | 운영 NCP→웹→관리자→워커 | 193개 원본에 버전 정보 존재 | 없음 |
| 실제 요청 생략 | 분당 타이머 자연 실행 | 빈 응답 후 `empty_backoff` 생략, 종료 코드 0 | 실제 기술 실패 업보 재처리는 새로 유발하지 않음 |
| 실제 백업 검사·재실행 | 승인된 테스트 워크스페이스 최근 일일 백업 1개, 격리된 로컬 상태 | 첫 실행 1개 검사·내용 변경 0, 두 번째 1개 생략·파일 요청 0 | 실사용 계정 전체 보존기간 작업은 강제 실행하지 않음 |

Preview 승격 때 플랫폼이 새 운영 배포 ID를 생성하여 ID 검사가 실패했다. 즉시 이전 배포로 복구한 후, 새 배포의 16개 소스가 원래 후보와 동일함을 대조하고 해당 ID를 승격했다. 이후 인증된 운영 목록 조회와 테스트 백업 재실행을 통과했다. 정확한 배포 ID·복구 파일·원본 해시는 비공개 운영 증거에 보존한다.

## 사용자 영향과 복구

- 최초 후원 처리·사용자 분류 대기 처리 방식은 그대로다. **기술적 재시도 큐가 오래 비어 있다가 새 작업이 들어오면 발견까지 명목상 최대 5분**이 걸릴 수 있다. 실제 시간에는 타이머 지연과 요청 시간이 더해진다. 작업 발견 이후는 기존 분당 처리다.
- 유휴 상태가 충분히 이어질 때 큐 요청은 분당 1회에서 5분당 1회로 줄어드는 설계다. 실제 전체 비용 80% 절감을 의미하지 않는다.
- 백업 생성 주기·복원 자료·보존기간은 그대로다. 첫 전체 실행은 성공 이력이 없으므로 기존처럼 모두 검사한다. 다음 정기 작업과 24시간/30일 절감률은 아직 관측하지 않았다.
- 오류가 나면 NCP 복구 디렉터리의 이전 retention 스크립트를 복원하고 이번 systemd drop-in을 제거한 뒤 daemon-reload한다. 기존 분당 curl 작업으로 돌아간다. 워커는 기록한 직전 배포를 승격한다. DB의 추가 메타데이터는 이전 코드와 호환된다. 캐시 기록은 백업 본문이 아니다.

## 제거·보존한 파일과 근거

레거시 파일이나 사용자 백업은 삭제하지 않았다. 변경은 워커 2개 파일, NCP 정리 스크립트와 새 재시도 실행기/drop-in, 추가 메타데이터 SQL, 검사·문서에 한정했다. 인증값은 기존 저장 위치에서 사용하며 게시 파일에 포함하지 않는다.
