## 목적과 변경 전 문제

장기 관측의 경과 시간을 성공으로 계산하지 않고, 실제 계정별 공통 수신 구간과 오류·회수·대조 공백을 구분하여 운영 채택 여부를 판단한다. 이전 검수에서는 한 계정만 수신했고, 관측기 오류로 중단되어 다중 계정 교차 검증이 미완료였다.

## 변경 내용과 소유 구성요소

이번 변경은 검수 문서와 연결 기록이다. 현재 구간과 이전 다섯 구간의 연구 JSONL을 읽기 전용으로 내려받아 비공개 로컬에 보존했다. 누적 comparison 스냅샷을 합산하지 않고 세션별 최종 session_end만 합산했다. 각 세션의 양쪽 received = matched + only + 종료부 pending 관계도 검사했다.

공개 문서에서는 운영 대상 두 계정을 A/B로 표시한다. 계정 매핑, 원격 위치, 실행 receipt와 원본 증거는 공개하지 않는다.

### 격리, 지연, 자원 및 연속성

- 네 세션 모두 실제 컨테이너 격리 검사 통과 및 종료 후 회수 확인. 읽기 전용 파일시스템, 비특권 UID, 호스트 볼륨 없음, 자원 제한과 비밀 환경변수 부재를 확인했다.
- 기존 방 소유자 상태 표본 총 2,608개에서 불일치 0. 두 계정 동시 관측에서 교차 혼선 징후는 확인되지 않았다. 세 번째 계정 실수신·강제 장애·악의적 경계 침범 시험까지 증명한 것은 아니다.
- 후보 도착 시각에서 기존 CDP 관측 시각을 뺀 버킷: `(-1000,-100]` 1개, `(-100,-20]` 76개, `(-20,0]` 7,303개, `(0,20]` 220개, `(20,100]` 45개, `(100,1000]` 1개. 7,523/7,646개가 `(-20,20]ms`에 있었다. 이는 관측 도착 차이이며 DB·업보 정리·화면 반영 속도가 아니다.
- 후보 프로세스 RSS: A 74.32~78.11 MiB, B 70.59~76.95 MiB. heapUsed는 각각 8.35~9.50, 8.36~9.64 MiB. 5,219개 텔레메트리 표본에서 상한 내였으나 더 긴 기간의 누수 부재를 보증하지 않는다.
- Docker 후보 메모리 표본 중앙값은 A 27.41 MiB / B 24.12 MiB, PIDs 각 11. CPU 중앙값 0.00%, 최대 0.18%로 표시됐다. 0.00은 반올림 값이며 실제 사용량 0이 아니다. Docker 메모리와 프로세스 RSS는 다른 측정치다.
- 기존 전체 컨테이너 메모리 중앙값은 같은 표본 묶음에서 684.7 / 679.3 MiB였다. 기존은 여러 계정·DB 전송·큐·관측 보조까지 포함하고 후보는 계정별 수신 전용이다. 단순 비율을 절감률로 사용하지 않는다. 500명 부하 검사는 수행하지 않았다.

- 각 계정의 제한된 세션 종료 후 재접속 성공. 기존 후보 종료 신호부터 다음 ready까지 A 약 107초, B 약 107초의 공백이 있었다. 이는 실패 복구·토큰 갱신의 완전한 검증이 아니며, 후보 단독 운영에서는 이 공백의 후원 수신을 보장할 수 없다.

### 중단과 재현 결함

1. **본문 없는 14바이트 프로토콜 메시지와 비호환.** `tools/soop-direct-lab/protocol.mjs`의 `decodePackets`는 15바이트 미만 및 본문 길이 0을 거부한다. 고정 해시 공식 SDK를 그대로 실행한 합성 소켓 검사에서 14바이트 keepalive 뒤 채팅 수신 지속과 14바이트 방송 종료 코드 뒤 chatinfo 재조회가 확인됐다. 같은 바이트를 후보 파서에 넣으면 `invalid_packet_size`가 발생한다. 기존 자동 검사에서 사용한 `encodePacket(0)`은 본문 구분자를 포함하는 15바이트여서 이 차이를 검출하지 못했다.
2. **실제 두 계정의 관측이 오류 중단 상태다.** A는 9월 27일 03:41:03 KST 후보 `invalid_packet_size`, B는 05:35:15 KST 기존 프레임 관측기 `original_packet_decode_failed`로 종료됐다. B의 메타데이터는 opcode 2, 디코딩 후 14바이트다. B 오류는 WebSocket ping/pong 제어 프레임이 아닌 binary 데이터 프레임에서 발생했다. 실패 원문·헤더 코드는 보존하지 않아 이것이 합성 재현과 동일한 방송 종료 메시지였는지는 확정할 수 없다. A는 크기 메타데이터도 없어 동일 원인이라고 묶지 않는다.
3. **동시각 기존 SDK 401 기록.** A 03:41:03.543, B 05:35:15.080 KST에 기존 경로에도 `sdk_error`, `error:__401_`가 남았다. 후보 종료와 거의 같은 시각이지만 HTTP 요청 대상·인증 만료 원인까지 이 로그로 확인되지는 않는다. 단순 후보 파싱 오류만 있었다거나 기존 수집기가 계속 정상 수신했다고 단정하지 않는다.
4. **관측기의 소켓 선택 범위가 페이지 단위다.** `soak-monitor.mjs`는 올바른 계정 페이지를 확인하지만 `Network.webSocketFrameReceived/Closed`를 특정 requestId로 제한하지 않는다. 같은 페이지의 별도 소켓 프레임·종료가 비교나 중단에 들어갈 가능성이 남는다. 코드 리뷰로 확인한 경계 문제이며 실제 혼선 발생 증거는 없다.

두 중단 직전 기존 상태 표본은 connected, pending 0, deadLetters 0, roomMatches true였다. 08:40 KST 현재 세 계정의 기존 경로는 방송 대기이고 큐 pending/deadLetters는 0이다. 연구 서비스 active는 테스트 대상의 대기 루프가 남아 있기 때문이며, 운영 두 계정은 needs_review로 멈췄고 후보 컨테이너 잔류는 0이다. 서비스 active를 수신 정상으로 표현하지 않는다.

## 사용자 영향과 복구

기존 Chromium 경로만 운영 데이터를 반영하는 상태를 유지했다. 후보에 쓰기 권한을 주거나 운영 수집기로 승격하지 않았다. 기존 소스·운영 설정의 변경이 없어 이번 문서 작업 자체의 서비스 롤백은 필요 없다.

운영 채택을 위해 닫아야 할 항목은 다음과 같다.

1. 빈 본문 제어 메시지의 정확한 계약을 지원하고 손상된 헤더·잘린 데이터 거부는 유지한다. 해당 입력을 고정 SDK 대조와 감독기 방송 종료/다음 방송 재개 검사에 추가한다.
2. 실패 메타데이터를 원문 없이 보완하고 비교 소켓을 명시적으로 제한한다. 기존 401의 원인을 확인하며 오류 안전 중단을 무조건 재시작으로 대체하지 않는다.
3. 수정 구간을 분리해 실제 종료·다음 방송·토큰 만료 경계·네트워크 단절 복구를 확인한다. 정상 세션 재개 시 107초 대조 공백도 따로 해결/평가한다.
4. 승인된 테스트 워크스페이스에서 후보 이벤트의 기존 분류기·내구성 전송·중복 방지·DB·업보/OBS 종단 검증을 완료한다. 실방송 관측만으로 수신 전용 후보의 운영 전송을 입증할 수 없다.

판정은 **수신 방식의 가능성과 두 계정의 실제 비교는 확인, 현 구현의 운영 전환은 차단**이다. 추가 관측 시간만 늘리는 것으로 위 구현·검증 누락을 해결할 수 없다. 안전 중단된 후보는 재시작하지 않았으며, 캠페인 종료 정책도 변경하지 않았다.

## 제거·보존한 파일과 근거

삭제 없음. 실행 receipt, 여섯 구간의 증거, 집계, 제한된 중단 맥락, 합성 재현은 비공개 `.local/soop-direct-lab`에 보존했다. SDK 원본·계정 ID·메시지 원문·토큰·실행 주소는 게시하지 않는다.
