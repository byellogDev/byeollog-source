## 목적과 변경 전 문제

SOOP가 새로운 채팅 포트를 배정할 때마다 수동 방화벽 변경이 필요했다. SOOP 공식 응답에서 확인한 목적지만 자동으로 허용하고, 불명확한 요청은 중단하도록 구성한다.

## 변경 내용과 소유 구성요소

- 전용 API 키는 운영 서버 IP 한 곳에서만 호출하도록 제한했다. root 전용 파일과 systemd `LoadCredential`로 별도 제어기에 제공하며 수집 컨테이너에는 전달하지 않는다.
- 새 규칙은 검증된 공인 IPv4 `/32`와 TCP 단일 포트의 출발 통신이다. 기존 8개 규칙과 인바운드·SSH 제한을 보존한다.
- 그룹·연결 서버·기존 규칙을 대조하고 생성 의도를 먼저 기록한다. 결과가 불명확하면 중복 생성하지 않는다. 활성 연결 관측이 정상일 때만 자동 생성한 유휴 규칙을 정리한다.
- 실제 iwinv API가 소문자 예제의 `outbound`/`tcp`를 거절하는 것을 확인했다. 명세의 `OUT`/`TCP`로 수정하고 회귀 검사를 추가했다.
- 설치기는 컨테이너 GID에 대응하는 호스트 그룹, 소켓 권한, 독립 서비스와 관측 타이머를 구성한다. 게시된 키 권한의 세부 분리는 공급자에서 확인되지 않았으며 코드 제한을 공급자 권한 제한으로 표현하지 않는다.
- 승격기는 기존 이미지·환경·compose·마운트·보안 제한을 보존한다. 컨테이너 상태뿐 아니라 동일한 계정 집합의 최신 heartbeat와 준비 상태를 기다린다. 실패하면 이전 이미지와 설정을 복구한다.
- Discord 감시에 제어기 인증·허용 IP·API 한도·규칙 변경·관측 중단 원인을 연결했다. 실제 장애를 만들거나 테스트 알림을 발송하지 않았다.

최종 승격 명령부터 준비 검사 완료까지 79.03초였다. 이는 방송 대기 중의 배포 절차 시간이며 실방송 이벤트 손실 시간으로 해석하지 않는다. 후보 이미지와 승격 이미지의 SHA-256 일치를 확인했다.

첫 승격에서는 컨테이너 건강 판정 직후 계정 준비가 끝나기 전에 검사해 자동 복구가 작동했다. 실제 계정은 이후 정상 방송 대기에 도달했다. 준비 조건을 함께 기다리도록 보완하고 동일 이미지로 재시도했다. 모든 교체는 5계정 방송 대기를 확인한 뒤 진행했다.

## 사용자 영향과 복구

- 새 포트는 별도 제어기의 공식 응답 검증 후 목적지별로 허용된다. 기존 승인 포트와 방송 대기는 제어기 없이 동작한다.
- 최대 자동 규칙 24개, 생성 분당 6개, API 호출 간격 1.1초 제한. 제어기/API 장애·규칙 변조·불명확한 응답은 자동 허용을 보류하고 감시한다.
- 재발 가능성이 완전히 사라진다고 보장하지 않는다. 공급자 장애나 새로운 프로토콜·응답 변경은 검토가 필요하다.
- 복구 시 이전 compose·환경·이미지를 재적용하고 활성화 표식을 제거한다. 운영 큐와 수동 규칙은 유지한다. 자동 규칙은 소유 ID·마커·내용을 확인한 경우에만 정리한다.

## 제거·보존한 파일과 근거

사용자 데이터 삭제 없음. 이전 이미지·compose·환경·모니터와 사전 규칙 목록은 비공개 복구 자료로 보존했다. 키·응답 원문·회원 자료·`graphify-out`은 게시하지 않는다.
