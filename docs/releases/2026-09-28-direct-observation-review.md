## 목적과 변경 전 문제

이전 검수에서 빈 SOOP 메시지 파싱 실패로 관측이 멈췄다. 수정 직후 합성 검사와 방송 대기만 확인했던 항목을 실제 수신·방종·세션 교체·격리·자원 기록으로 다시 검증했다.

## 변경 내용과 소유 구성요소

운영 및 후보 코드 변경 없음. 연구 수신기·대조 관측기·감독기의 현재 구간 기록을 비공개로 보존하고 완료 세션과 실행 중 세션을 함께 집계했다. 실행 중 세션은 마지막 양쪽 대조 시각까지만 계산하며, 그 이후 단독 telemetry 증가분을 불일치로 오인하지 않는다.

## 검증

### 실제 수신과 연속성

공개 문서에는 계정 식별자 대신 관측 대상 A/B를 사용한다. A는 완료 세션 1개, B는 완료 세션 1개와 실행 중 세션 1개다.

| 항목 | 대상 A | 대상 B |
| --- | --- | --- |
| 연결 구간 KST | 9/27 19:02:44–23:27:35 | 9/27 16:59:39–21:54:26, 21:55:05–9/28 04:56:55 |
| 실제 연결 시간 합계 | 4시간 24분 50초 | 11시간 56분 37초 |
| 콘텐츠 프레임 일치 | 780 | 2,427 |
| 채팅 계열 / 일반 별풍선 이벤트 | 772 / 8 | 2,425 / 2 |
| 한쪽만 수신 / 대조 미결 | 0 / 0 | 0 / 0 |
| 확인 시점 상태 | 독립적으로 확인된 방송 대기 | 수신 중 |

- 총 **3,207건** 일치: 코드 5는 3,144건, 코드 109는 53건, 일반 별풍선 코드 18은 **10건**이다. 후원 건수는 이벤트 수이며 별풍선 개수가 아니다.
- 두 계정의 실제 동시 연결은 **4시간 24분 11초**다. 테스트 대상은 방송 대기로 세션 0개이므로 세 계정 동시 수신은 미검증이다.
- 두 완료 세션의 종료 꼬리 미결 및 공통 구간 밖 프레임은 각각 0건이다. 대조기는 준비 직후 1초를 제외하며 시작 전·세션 사이 공백의 수신까지 증명하지 않는다.
- 대상 B의 정상 제한시간 종료 후 다음 준비 완료까지 **38.916초** 공백이 있었다. 이전 후보 회수와 다음 세션 자동 시작·수신은 확인했지만, 이 공백에는 양쪽 대조가 없으므로 무손실 연속 수신을 주장할 수 없다. 기존 운영 수집은 계속되었다.

### 방종 처리와 격리

- 대상 A에서 9/27 **23:27:35 KST**, 양쪽 모두 **14바이트·본문 길이 0·코드 88·반환 코드 0**인 방종 신호를 기록했다. 파싱 오류 없이 후보를 회수하고 23:27:51에 기존 경로의 신선한 `broadcast_offline` 상태로 방종을 독립 확인했다.
- 전체 현재 구간에 파싱 오류·`needs_review`·원인 불명 종료·회수 실패 기록은 없다. 두 완료 세션 모두 후보 회수 성공이다. 현재 후보 컨테이너는 수신 중 대상 B의 1개다.
- 실제 연결된 세 세션 모두 격리 검사 통과: 계정별 컨테이너, UID 65534, 메모리 256 MiB/PIDs 32 제한, 호스트 마운트 0. 기존 방 식별 대조 **1,962회 중 불일치 0**이며 콘텐츠도 계정별 HMAC로 대조했다. 관측에서 혼선 징후가 없다는 근거이며 모든 공격 상황의 격리를 보증하는 것은 아니다.
- 설치된 후보/관측기/진입점 및 감독·대조 코드와 검사 파일 **7개 해시가 현재 배포 receipt와 일치**한다. 기존 운영은 Node 22.23.2이며 조회 시 전송 대기·dead letter는 0이었다.

### 속도와 자원

| 측정값 | 대상 A 후보 | 대상 B 후보 |
| --- | --- | --- |
| Node RSS 범위 | 72.6–76.0 MiB | 71.6–78.3 MiB |
| heap 범위 | 8.33–9.43 MiB | 8.37–9.49 MiB |
| Docker 메모리 중앙값 | 25.19 MiB | 27.31 MiB |
| Docker CPU 표본 중앙값 / 최대 | 0.00% / 0.14% | 0.00% / 0.13% |
| Docker PIDs | 11 | 11 |

각 세션 RSS는 초반 대비 마지막 약 2.3–3.4 MiB 높았고 heap은 9.5 MiB 이내였다. 소켓은 표본 전체 1개이며 타이머는 4–5개였다. 관측 범위에서 자원의 큰 증가 추세는 없었지만 장기 누수 부재를 확정하지 않는다. Docker 메모리와 Node RSS는 산정 기준이 달라 같은 값으로 취급하지 않는다. CPU 0.00%는 표본의 표시 정밀도이며 사용량이 전혀 없다는 뜻이 아니다.

기존 **전체** 수집 컨테이너는 같은 표본에서 메모리 567.3–772.9 MiB, PIDs 168–223이었다. 여러 계정의 Chromium·DB 전송·큐·관측 보조를 포함하므로 계정 하나의 수신 전용 후보와 단순 비율로 절감률이나 500명 수용량을 계산하지 않는다.

일치 프레임의 후보 수신 시각 − 기존 CDP 관측 시각은 **(-20, 0] ms 2,528건, (0, 20] ms 679건**이다. 20 ms를 초과한 후보 지연 표본은 없다. 이는 관측 지점의 시각 비교이며 CDP 전달 지연을 포함한다. 평균·p95 원시 지연, 서버 정리·DB·업보·OBS 도달 속도는 이 자료로 산출할 수 없다.

비교는 관심 콘텐츠 코드의 패킷 바이트 HMAC를 중복 개수까지 대조한다. 양쪽이 함께 받지 못한 이벤트, 전체 순서 보장, 실제 SDK 업무 변환 결과의 동등성까지 이 검사로 증명하지 않는다. 이번에는 코드/배포를 바꾸지 않았으므로 이전 합성 검사를 재실행한 것처럼 새 통과 건수를 추가하지 않았다.

## 사용자 영향과 복구

- 기존 Chromium 경로만 운영 데이터를 기록한다. 이번 작업은 조회와 문서 게시만 수행하며 사용자 동작·수집기 실행 상태를 변경하지 않았다.
- 이번 실제 방종 처리와 콘텐츠 대조는 통과했다. **운영 전환은 계속 보류**한다. 세션 교체 공백의 누락 방지, 방종 후 다음 방송 재개, 실제 네트워크 장애 복구·OAuth 갱신 경계, 후보→DB/업보/OBS 종단 검증이 남았다.
- 이번 구간에서 발생하지 않은 영상·미션·애드벌룬 등은 미검증이다. 이전 버전에서 관측한 후원 종류를 이번 수정본의 실적으로 합산하지 않는다.
- 새로운 불일치·파싱 실패·회수 실패는 기존 안전 중단 규칙을 유지한다. 장애 후보를 임의 재시작하지 않고 증거 확인 후 연구 서비스만 조치한다.
