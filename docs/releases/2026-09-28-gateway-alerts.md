# 수집 초기 대기 오탐·알림 순서 수정 · 2026-09-28

## 상태와 범위

- 상태: 운영 DB 반영 완료, 04:11 KST 이후 감시·전송 cron 성공 확인.
- 대상: 연결 감시 함수, 운영 알림 enqueue/전송 함수, 비공개 초기 대기 시각 표.
- 수집기·웹·Agent·후원 처리·기존 회원 데이터·cron 주기 변경 없음.
- 이전 기준: 운영 함수 정의를 비공개 보관하고 적용 직전 해시가 같은 경우만 변경했다. 설치 EXE r2 배포와 독립된 DB 수정이다.

## 목적과 변경 전 문제

첫 heartbeat가 없는 신규 수집 대상은 시간 초과 여부와 무관하게 즉시 장애로 판정됐다. 이번 사례는 대상 활성화 후 약 26초 만에 장애 알림이 생겼고, 수집기 시작 후 방송 대기 상태를 보고하면서 30초 뒤 복구됐다.

장애와 복구를 같은 전송 주기에 비동기 HTTP로 요청하면 Discord 도착 순서가 뒤집힐 수 있었다. 단순 정렬만으로 실제 전송 완료 순서는 보장할 수 없다.

## 변경 내용과 소유 구성요소

- 첫 heartbeat 부재를 처음 감지한 시각부터 150초를 유예한다. 실제 장애 판정은 150초 유예 이후 30초 감시 주기에 따라 이뤄진다. 계속 시작하지 못하면 장애 알림을 보낸다.
- 최초 시각은 별도 private 표에 한 번 기록한다. 일반 설정 수정으로 유예가 연장되지 않는다. heartbeat 수신 또는 비활성화 시 정리한다.
- 기존 heartbeat가 있는 연결은 방송 중 150초·방송 대기 600초 기준을 그대로 유지한다.
- 동일 장애의 알림이 HTTP 2xx 성공으로 확인된 뒤에만 복구 알림을 전송한다. 장애 전송이 영구 실패하면 복구만 따로 보내지 않는다.
- 15분 중복 제한 때문에 장애 알림이 생략된 경우 대응하는 복구도 생성하지 않는다. 실제 생성된 장애의 복구는 별도 중복 제한 때문에 누락되지 않도록 고유 키로 한 번만 만든다.
- 대기 중인 복구 알림은 다른 계정·주제의 전송을 막지 않는다. 기존 최대 5건 처리, 12회 재시도, 24시간 만료, 14일 보관 조건을 유지한다.
- 신규 표는 RLS 활성화, 일반 역할 권한 없음. 함수는 기존 owner·SECURITY DEFINER·빈 search_path와 비공개 실행 권한을 유지한다.

## 검증

| 항목 | 방법 | 결과 | 미검증 범위 |
| --- | --- | --- | --- |
| 기존 오류 재현 | 격리 PostgreSQL에서 기존 monitor 실행 | 첫 heartbeat 없음 → 즉시 장애 재현 | 실사용 계정으로 장애를 만들지 않음 |
| SQL 회귀 | PGlite 실제 migration 실행 | 13건 통과 | 실제 Discord 네트워크·다중 DB 세션 동시성 |
| 운영 정의 | 배포 함수 3개의 전체 정의 대조 | 검증 SQL과 일치 | 이후 다른 배포의 변경 |
| 운영 실행 | 반영 후 기존 cron 이력 | 연결 감시·알림 전송 성공, 미전송/실패 0건 | 신규 가입의 실제 알림 재현은 수행하지 않음 |
| 권한 | ACL·RLS 확인 및 합성 권한 검사 | private, postgres 전용 유지 | 기존 전체 DB 보안 재감사 아님 |
| 소스 검사 | verify-source | 기존 기준 1,183개·의도 변경 41개, 실패 0 | 신규 SQL 실행 검증은 위 별도 결과 |

Supabase 보안 Advisor의 신규 표 관련 항목은 RLS 활성화 후 정책 없음 안내다. 이 표는 서버 내부 전용으로 클라이언트 접근을 의도적으로 전부 차단하므로 허용 정책을 추가하지 않았다. [안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy).

비동기 요청은 트랜잭션 commit 이후 실행되며 요청 ID 자체는 성공 증거가 아니다. [pg_net 공식 설명](https://supabase.com/docs/guides/database/extensions/pg_net)을 기준으로 성공 응답을 확인한다.

## 사용자 영향과 복구

초기 연결 대기 때 불필요한 장애 알림이 줄고, 복구 알림은 장애 알림 뒤에 전송된다. 기존 전송 결과 확인이 재시도 스케줄을 따르므로 복구 알림은 정상 전송에서도 보통 2~3분 추가로 늦어질 수 있다. 실제 수집·후원 처리 속도에는 영향을 주는 변경이 없다.

수정 후 실제 신규 활성화와 Discord 표시 순서는 자연 발생 이벤트로 추가 확인할 범위다. 이를 확인하려고 운영 장애나 사용자 알림을 임의 생성하지 않았다.

문제가 발생하면 비공개 저장한 이전 함수 3개의 정의를 복원한다. 추가한 private 표는 복구 시 우선 보존하며 기존 사용자 데이터 삭제나 수집기 재시작은 필요하지 않다. 이전 정의로 복구하면 초기 오탐·알림 역전 가능성도 되돌아온다.

## 제거·보존한 파일과 근거

기존 migration과 장애 이력을 보존했다. 새 migration·격리 DB 검사·의존성 lock·CI 단계·릴리스 문서만 추가했다. 인증값·회원 식별자·원문 로그·복구 영수증은 공개 저장소에서 제외한다.
