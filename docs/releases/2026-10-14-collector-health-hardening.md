## 목적과 변경 전 문제

SOOP가 TCP 8041을 할당했지만 허용 목록에는 9001만 있어 연결이 반복 실패했다. 방화벽 복구 이후에도 감시는 `connecting`을 오류로 세지 않아 재시도를 실제 복구로 오판할 수 있었다. 실패 상태와 포트 관측을 지속해서 보존하도록 수정했다.

## 변경 내용과 소유 구성요소

- `channel_health.py`: 실패 기억, 새 연결 90초 유예, 실제 연결 또는 방송 종료 증거로만 해제. stale·누락·잘못된 채널 상태는 정상으로 간주하지 않는다.
- `infra-health.py`: 60초 이내 worker 기록과 컨테이너의 외부 TCP 소켓 관측. 미허용 포트는 번호만 보존하며 소켓 종료로 경고 근거가 사라지지 않는다.
- `patch-ops-monitor.py`: 신선한 상태 두 건으로 복구 확인, 재시도 시 정상 연속 횟수 초기화, 잘못 대기 중인 복구 알림 취소, 포트 번호를 포함한 별도 경고. health stale 기준 9분에서 90초로 보완.
- 로컬 점검 5분에서 30초로 단축. 외부 API·DB 집계·알림 주기는 약 2분으로 유지한다.
- 해시·후보 검사·원자 교체·이전 파일 복구를 포함한 감시 전용 배포 절차를 정식 소스로 추가했다.

## 사용자 영향과 복구

프로그램 재설치나 사용자 설정 변경은 없다. 실패 후 연결을 재시도한다는 이유만으로 복구 알림이 나오지 않으며, 실제 확인 전까지 장애를 유지한다. 감시 상태는 프로세스 재실행 후에도 보존한다.

공식 SDK는 API가 반환한 포트에 1을 더해 TLS로 접속한다. [공식 연결 문서](https://developers.sooplive.com/docs/chatsdk/connection)와 [SDK](https://static.sooplive.com/asset/app/chat-sdk/sooplive-chat-sdk.js)에서 완전한 포트 범위는 확인하지 못했다. 확인된 8041·9001과 동적 목적지 허용을 유지하고 새 미허용 포트를 감지한다. **향후 모든 장애의 사전 방지 또는 무누락을 보증하지 않는다.**

30초는 로컬 점검 간격이며 알림은 약 2분 주기의 두 표본 및 기존 재알림·재시도 정책에 따른다. 짧은 소켓 시도는 점검 사이에 끝날 수 있다. 포트 대조 기준은 승인 정책이며 클라우드 방화벽의 실시간 자동 조회나 자동 개방은 아니다.

복구 파일·배포 해시·정확한 서버 경로는 보호된 운영 기록에 보존했다. 후보의 `deploy-health.py rollback`으로 이전 감시·타이머 파일을 복구하며 다른 버전으로 변경된 파일은 덮어쓰지 않는다. 수집 연결과 기존 알림 DB는 유지한다. [운영 절차](../../operations/iwinv/MONITORING.md).

## 제거·보존한 파일과 근거

회원 데이터·후원 큐·원문·알림 DB 삭제 없음. 이전 감시 파일을 보존하고 후보 상태는 운영 상태와 분리했다. 비공개 원문·운영 인증값·개별 계정 식별자는 게시하지 않는다.
