# 신규 시청자 업보 저장 수정 · 2026-10-04

## 상태와 범위

- 상태: 운영 DB 반영, 웹·관리 런타임 후보 검증 후 승격.
- 확인 날짜: 2026-10-04 KST. 배포 ID·해시·시각·복구 원본은 비공개 운영 기록에 보존합니다.
- 대상: 업보와 시청자 정보의 저장 순서 및 저장 후 화면 처리. Agent·수집기·후원 원본은 변경하지 않습니다.
- 이전 기준: [룰렛 대기 자동 종료](2026-10-02-roulette-timeout.md). 해당 기능은 유지합니다.

## 목적과 변경 전 문제

시청자 등록 정보가 없는 SOOP ID로 업보를 추가하면 복합 외래키 검사에 실패했습니다. 화면은 업보 저장 후 시청자를 등록하려고 했으므로 DB가 요구하는 순서와 반대였습니다. 운영 DB 로그에서 해당 오류를 확인했고 동일 제약을 가진 테스트 DB에서 재현했습니다.

## 변경 내용과 소유 구성요소

- DB의 비공개 `SECURITY INVOKER` 트리거가 업보 추가 또는 시청자 ID 변경 시 같은 워크스페이스의 시청자 정보를 먼저 준비합니다. 두 저장은 동일 트랜잭션에 포함되므로 업보 저장이 실패하면 새 시청자도 남지 않습니다.
- `(workspace_id, soop_id)`로 충돌을 처리합니다. 기존 시청자의 별명·닉네임·방송국 주소는 덮어쓰지 않고 계정별 외래키·권한·RLS를 유지합니다. 함수 직접 실행 권한은 앱 역할에서 차단합니다.
- 일반 완료 수량 수정에는 새 트리거가 실행되지 않습니다. SOOP ID 없는 업보도 기존대로 저장합니다.
- 화면은 업보 저장 뒤 생성된 시청자를 조회합니다. 이미 DB에 생성한 시청자를 다시 INSERT하던 요청을 제거했습니다. 저장 후 조회가 실패하면 저장된 업보 ID를 유지해 재시도는 수정을 수행합니다.
- 공유 화면 소스와 생성물을 네 앱에 동기화했고 실제 웹·관리 런타임만 배포합니다. 원래 운영 소스의 다른 차이는 그대로 보존합니다.

## 사용자 영향과 복구

- 처음 등록하는 시청자에게도 바로 업보를 추가할 수 있습니다. 이미 열려 있던 화면은 입력 내용을 따로 보관한 뒤 새로고침해야 새 저장 후 처리 코드가 적용됩니다.
- 기존 시청자의 별명 변경 확인·업보 수량 충돌 방지·첨부파일 저장은 유지합니다.
- 복구할 때는 이전 화면과 DB 트리거의 의존 관계를 함께 확인합니다. 비공개 복구 SQL로 트리거·함수를 제거할 수 있으나 먼저 기존 화면을 복원해야 합니다. 생성된 정상 시청자·업보를 일괄 삭제하지 않습니다.
- 실제 사용자 PC의 저장 확인은 별도입니다. 테스트 계정의 운영 DB 저장과 로컬 화면 로직 검증을 완료했습니다.

## 제거·보존한 파일과 근거

파일 삭제 없음. 비공개 배포·복구 증거만 `.local`에 저장하며 공개 기록에는 인증값·회원 정보·오류 원문을 넣지 않습니다. 테스트는 합성 식별자만 사용합니다.
