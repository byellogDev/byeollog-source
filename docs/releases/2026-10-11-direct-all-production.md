## 목적과 변경 전 문제

기존 정책은 한 계정만 직접 연결하고 나머지는 SDK를 사용했다. 전체 전환 후 새로 추가된 계정이 다시 SDK를 사용하지 않도록 기본 수집 방식을 정책으로 지정한다. 사용자가 수락한 내용 일치와 직접 경로의 실제 운영 저장 결과를 근거로 전환하며, 미검증 사항을 완료로 바꾸지 않는다.

## 변경 내용과 소유 구성요소

- gateway `transport-policy.mjs`: schemaVersion 2에서 `defaultTransport`, `directWorkspaceIds`, `sdkWorkspaceIds`를 검증한다. 기본 direct와 빈 예외 목록을 운영에 적용한다.
- 기존 schemaVersion 1의 명시 계정 목록과 정책 파일 부재 시 SDK 복구 동작은 호환 유지한다. 잘못된 정책은 조정 전에 거부해 기존 작업을 유지한다.
- 새로운 활성 계정은 조정 시 기본 direct를 선택한다. SDK 예외로 지정한 계정만 기존 방식으로 복귀할 수 있다. 계정 작업 교체는 이전 작업의 내구성 큐 저장을 기다린 뒤 진행한다.
- 프로토콜·파서·연결 교체·암호화 전송 큐는 기존 검증 코드 그대로다. 후보 이미지는 직전 운영 이미지에서 정책 모듈 한 파일만 바꿔 생성했다.
- SDK 비교 연구 unit은 정지하고 부팅 자동 실행을 해제했다. 기존 SDK 기준이 사라진 뒤 direct 두 개를 비교하는 잘못된 검증과 중복 접속을 막기 위한 조치다. 원문·설정·이전 비교 결과는 보존하며 운영 수신·저장에 대한 후속 검증은 계속할 수 있다. 비교 연구의 종료를 모든 안전성 검증 완료로 해석하지 않는다.

운영 소스 6개 해시가 후보와 일치하고 환경변수 값·볼륨·사용자·보안 및 자원 제한이 보존됐다. 컨테이너 healthy, 재시작 카운터 0·OOM 없음, Chromium 프로세스 0개다. 연구 비교 unit은 inactive/disabled이고 예약 타이머도 비활성이다. 배포 전후 모든 계정은 방송 대기였다.

최초 배포에서 5개 direct 작업은 정상 기동했지만 프로세스 검사 명령이 Docker에 필요한 PID 열을 누락해 이전 이미지·정책으로 자동 복귀했다. PID와 프로세스명만 조회하도록 검사 명령을 정정하고, 이전 1 direct/4 SDK·방송 대기·빈 큐 복귀 및 수정 명령의 성공을 확인한 뒤 동일 후보를 재적용했다. 제품 코드의 추가 수정이나 검사 생략은 없었다. 최초 시도·복귀 자료는 비공개로 보존한다.

## 사용자 영향과 복구

- 모든 활성 계정이 SDK/Chromium 대신 직접 WebSocket으로 운영 수집한다. 기존 후원 저장·업보·풍벽지 전달 경로와 권한은 유지한다.
- 배포는 방송 대기·빈 큐 조건에서 공용 컨테이너를 교체했다. 이전 시도의 자동 복귀를 포함한 재기동을 기록하며 무중단 배포라고 주장하지 않는다.
- 특정 계정 복귀: schemaVersion 2의 `sdkWorkspaceIds`에 해당 계정을 지정하고 직접 예외와 중복되지 않게 한다. 다음 조정 주기와 이전 작업 정리 후 적용된다. 방송 중 복귀에는 재연결 공백이 생길 수 있다.
- 전체 정책 복귀: 기본값을 SDK로 바꾸고 예외를 명시하거나 보존한 이전 schemaVersion 1 정책을 복구한다. 이미지까지 복구하면 이전 이미지·Compose와 이전 정책을 함께 복원한다. 새 schemaVersion 2 정책만 남긴 채 구 이미지를 실행하지 않는다.
- SDK 코드·직전 이미지·Compose·정책·연구 원문은 보존한다. 최신 암호화 outbox와 인증값을 유지하며 오래된 큐 사본을 덮어쓰지 않는다.
- 무이벤트 교체 성공·실제 장애 주입 복구·미발생 후원 유형·각 고객 OBS 화면은 이번 전환으로 새로 검증되지 않았다. 신규 경로 기본 적용은 최대 수용 인원이나 완전 무손실 보장이 아니다.

## 제거·보존한 파일과 근거

데이터 삭제 없음. SDK 의존성·이미지와 원문을 복귀 자료로 보존하고 실제 SDK 작업·브라우저 실행만 없앤다. 사용자 식별자와 서버 접속 정보는 공개하지 않는다.
