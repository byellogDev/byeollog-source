# 위플랩 URL 수신 후보 비교 준비

- 서버 타이머 시작: **2026-10-09 19:00 KST**. 서버에서 해당 예약 시각과 active 상태 확인.
- 자동 종료 시각을 임의로 두지 않는다. 사용자 종료 요청 또는 안전 한도 도달까지 수신한다. 방송 대기 시간을 실검증 시간으로 세지 않는다.
- 운영 컨테이너·OAuth·DB 쓰기·OBS·위플랩 설정 변경 없음. 운영 컨테이너 시작 시각이 배포 전후 동일했다.
- 비공개 실행 기준: `.local/weflab-observer-a-20261009/config.private.json`, `deploy-receipt.private.json`. 오버레이 URL과 회원 정보는 Git에 넣지 않는다.

## 구조

`tools/weflab-lab/observe.mjs`는 계정·프리셋·허용 호스트를 확인하고 main 및 afreeca Socket.IO 채널에 구독만 요청한다. 화면 렌더링, platform/start 요청, 봇 전송, 결과 생성, 운영 저장은 하지 않는다. **join_sent는 구독 요청 기록이며 실제 후원 전달 확인이 아니다.** 기존 방송 오버레이가 플랫폼 연결을 유지하는 상황에서 join만으로 실제 후원이 전달되는지도 이번 방송의 검증 항목이다.

연구 컨테이너는 기존 이미지의 Node를 사용하되 운영 환경변수와 볼륨을 받지 않는다. 별도 코드·비공개 설정·연구 증거 디렉터리만 사용하고 포트를 열지 않는다. CPU 0.25코어, 메모리 192MiB, PID 48개로 제한한다. root가 아닌 사용자, read-only rootfs, capability 제거, no-new-privileges를 적용한다. 연구 폴더는 소유자만 읽을 수 있다.

원문 프레임을 해석 **이전**에 보관한다. 정상화 이벤트·규칙 스냅샷·연결/단절·오류 원문·30초 간격 RSS/heap/CPU를 JSONL로 남긴다. 파일당 16MiB, 총 512MiB에서 자동 삭제 대신 needs_review로 중단한다. 네트워크 단절은 최대 60초까지 지수 지연하여 재연결한다. 계정 혼선·스키마 오류·같은 UID의 내용 변경은 자동 재시작하지 않는다. 같은 경로의 프로세스 중복은 배타 잠금으로 막는다.

## 대조 방법

1. 저장된 전체 원문을 비공개로 회수한다. `node .local/weflab-observer-a-20261009/read.mjs --download`.
2. 정확한 workspace_id와 같은 종료된 구간으로 기존 DB 후원·룰렛 결과를 조회한다. `export-baseline.mjs`는 기존에 승인된 로컬 자격증명을 인자로 받아 GET만 사용하고 500건씩 페이지를 끝까지 읽는다. 서버 연구 프로세스에 DB 비밀키를 주지 않는다. 실행 중인 구간의 늦은 저장은 후속 조회로 구분한다.
3. `node tools/weflab-lab/compare.mjs <private-config> <evidence-dir> <private-baseline> <private-report>`로 비교한다. baseline은 `{owner,workspaceId,from,to,complete:true,donations,results}` 형식이다.
4. 계정·후원자 ID·수량·수신시각 ±120초 조건이 서로 유일할 때만 대응한다. 후보 UID 반복과 동일 UID 내용 충돌을 구분한다. 닉네임/수량만으로 매칭하거나 모호한 후원을 순서대로 소비하지 않는다.
5. 편측 건은 즉시 누락으로 확정하지 않는다. 후보 연결 시간, 기존 수집 상태, 종류 지원, DB 저장 지연을 조사한다. 현재 자동 정상화 대상은 일반 SENDBALLOON이며 다른 후원 유형은 원문을 보존하고 미검증으로 남긴다.
6. `databaseWriteMinusReceiptMs`는 기존 DB created_at과 후보 수신시각 차이다. 기존 수집기의 최초 수신시각이나 네트워크 속도와 동일하지 않다. 공통 구간과 시계 차이도 확인해야 한다.

## 룰렛 결과의 특별 조건

사전 테스트 계정에서 실제 표시 결과와 URL 기반 조회 결과 1건이 일치했다. 이것을 관측계정A 실방송 검증으로 합산하지 않는다.

`roulette_result` API는 저장값이 없으면 **추첨을 생성할 수 있다**. 후보가 먼저 호출하면 실제 오버레이의 처리에도 영향을 줄 수 있으므로 실시간 관측기는 이 API를 호출하지 않는다. 단순 대기 시간 경과를 읽기 안전성으로 간주하지 않는다.

`lookup-confirmed-result.mjs`는 별도 검토 후에만 실행한다. 유일하게 대응된 후원의 기존 최종 결과, 기대 회차·실제 결과 수, 마지막 결과 60초 경과, 이벤트 당시와 현재 규칙 해시 일치를 요구한다. 첫 버전은 단일한 정확 수량 규칙만 지원한다. 범위·규칙 변경·모호한 대응은 조회하지 않는다. `--confirmed-result`가 필요하며 배타 receipt를 먼저 만들어 요청 결과가 불명확해도 재시도하지 않는다. 이 조건도 제공자 내부 저장소의 보장을 대신하지는 않는다.

- `api=sql/mem`은 저장 결과 재사용 관측으로 분류하고 기존 결과와 별도 비교한다.
- `api=save` 또는 모르는 응답은 결과 생성 가능성으로 needs_review이며 검증 성공으로 계산하지 않는다.
- 기존 결과가 없으면 룰렛 결과는 미검증이다. 후원 이벤트 관측 자체는 계속한다.
- 동일 결과의 여러 회차 순서·공식 룰렛 문구 변환은 실제 자료로 확인해야 한다.

## 현재 검증과 한계

- 합성 단위/계약 검사 13건 통과: 계정/호스트 고정, 테스트 제외, UID, 모호한 매칭, 중복과 충돌, 페이지 미완료 거부, 결과 생성 응답 구분.
- 서버 사전 연결 15초: 두 채널 연결·join 전송, 정상 종료, 결과 API 호출 0회. 실제 후원 0건. 사전 증거는 별도 폴더이며 본 관측과 섞지 않는다.
- 실방송 후원·룰렛 결과·장기 재연결·계정 혼선 부재·수집 성능은 아직 미검증이다. 자동화는 시작 이후 상태와 최초 유의미한 실제 비교를 확인하고, 의미 있는 결과/실패만 알린 뒤 점검을 일시 중지한다.

## 운영 절차와 복구

운영 수집기 재시작 없이 연구 서비스와 타이머만 중지할 수 있다. 단위 이름은 비공개 receipt에 기록되어 있다. 안전 중단 시 원문부터 확인하고 무조건 재시작하지 않는다. stale lock도 소유 프로세스 종료를 확인하기 전 제거하지 않는다. 연구 증거·사전 테스트 자료를 삭제하거나 운영 DB를 복원할 필요가 없다.
