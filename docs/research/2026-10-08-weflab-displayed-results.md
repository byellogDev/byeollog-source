# 위플랩 실제 표시 결과 수집 검토

## 결론과 범위

2026-10-08 소스·공식 문서 검토. 사용자 정정: 방송인은 OBS만 사용하지 않는다. 따라서 **OBS 직접 연결을 공통 수집 방식으로 채택하지 않는다.** 이번에 확인한 OBS 연결은 해당 프로그램 사용자에게만 가능한 선택지다. 공통 경로는 아직 확정하지 않았으며 실행 가능한 관측기를 구현하거나 방송 프로그램에 연결한 결과도 아니다.

사용자가 원하는 기준은 시청자가 방송 화면에서 보는 룰렛 결과다. 위플봇 채팅과 기존 별록 결과는 작동 조건에서 제외한다. 방송용과 경쟁하는 두 번째 추첨 브라우저나 추첨 API 재호출도 제외한다. [앞선 경로 조사](2026-10-08-weflab-independent-results.md)의 결과 알림 역시 실제 표시 렌더러가 사용한 결과와 연결되는지 확인해야 한다.

## 방송 프로그램에 종속되지 않는 후보

| 경로 | 사용자 흐름 | 남은 핵심 검증 |
| --- | --- | --- |
| 위플랩의 확정 결과 전달 경로 | 기존 방송 설정을 유지하고 주소를 등록 | 제공된 주소 권한으로 수신 가능한지, 실제 렌더러의 결과인지, 봇 송신과 독립적인지. 현재 미확인 |
| 기존 표시 페이지의 결과 전달 기능 | 실제 표시 인스턴스가 별록으로 결과를 전달 | 위플랩의 공식 지원·협력이 있으면 공통 경로가 될 수 있으나 현재 지원 확인 없음. 일반 주소나 외부 iframe만으로 타 출처 내부 값을 읽을 수 있다고 가정하지 않음 |
| Agent가 단일 표시 렌더러를 소유 | Agent에서 위플랩을 한 번 실행하고 그 영상·음성을 별록 로컬 오버레이 주소로 방송에 전달 | 기존 직접 위플랩 소스를 교체해야 함. 투명도·음성·지연·부하·프로그램별 브라우저 소스 호환 검증 필요. 구현·성공 근거 없음 |
| 방송 프로그램별 기존 렌더러 관측 | 기존 소스를 유지하며 지원 프로그램에 관측 어댑터 설치 | OBS 디버깅 문서는 확인했지만 타 프로그램은 각각 별도 조사 필요. 공통 기본 기능으로 선언하지 않음 |

공통성이 가장 좋은 것은 위플랩이 실제 선택 결과를 외부에 전달하는 경로다. 이것이 없거나 접근할 수 없다면 단일 렌더러를 Agent가 소유하는 대안과 프로그램별 어댑터의 비용을 비교한다. 현재 URL만으로 모든 프로그램의 실제 표시 결과를 읽는 데 성공했다고 주장하지 않는다. 사용자는 방송별로 OBS 전용 설정을 해야 한다는 결정을 하지 않았다.

대상은 위플랩 공개 `main.js?ver=20261003210115`, SHA-256 `a92646704a5fb478dd32de683045eeb5ef4108a59061abe7a06865381d6e890e`다. 원본은 비공개 보관하며 소스 발견을 실제 장애 발생으로 해석하지 않는다.

| 소스 지점 | 확인한 동작 | 관측 설계에 미치는 영향 |
| --- | --- | --- |

| `roulette_msg` | 표시 처리 경로에서 조건에 따라 별도 봇 전송 요청 | 봇 전송 성공 없이도 렌더러 결과를 수집하는 경로를 검토할 근거 |

## OBS에 한정하여 확인한 연결 방법

OBS 공식 문서는 기존 CEF 브라우저 소스에 Chromium 원격 디버깅으로 접속하는 방법과 `--remote-debugging-port`, `--remote-allow-origins` 실행 인자를 제공한다. 새 오버레이 페이지를 여는 방식이 아니다. Agent의 별도 CDP 어댑터가 지정된 기존 소스만 관찰하도록 설계할 수 있다.

현재 Agent에는 인증을 지원하는 로컬 전용 `ObsWebSocketClient.cs`가 있다. 장면·소스 상태 확인에 재사용할 수 있으나 일반 OBS WebSocket이 브라우저 HTTP 응답 본문을 제공하는 것은 아니다. 로그인용 WebView2 역시 OBS의 CEF 인스턴스와 다르다.

이 PC의 OBS 파일 버전은 32.2.1이다. 이 버전과 스트리머 PC에서 실제 디버깅 연결, 응답 본문 읽기, 소스 식별·재접속을 아직 검사하지 않았다. 활성화에는 OBS 실행 설정 및 재시작이 필요할 수 있다. 이번 검토에서 실행 설정·방송 장면을 변경하거나 OBS를 재시작하지 않았다.

접속은 로컬로 한정하고 실제 리슨 주소·외부 차단을 검사한다. origin 허용은 인증 대체물이 아니며 디버깅 연결은 페이지 제어 권한도 있으므로 외부 공개·와일드카드 origin·임의 스크립트 전달을 금지한다. 승인된 소스만 선택하고 다른 브라우저 소스·도크는 수집하지 않는다. 후보는 요청 재전송·캐시 비활성화·네트워크 가로막기·중단점 없이 실제 응답을 읽는 방식부터 시작한다.

## 관측 계약 초안

`계정 + 오버레이 인스턴스 + 로드 세대 + 후원 UID + 회차`로 증거를 연결한다. 재생·재로드는 별도 표시 시도로 남기되 원래 후원/회차의 업무 처리를 중복 생성하지 않는다. 여러 실제 소스가 같은 주소를 사용하면 임의로 하나를 선택하지 않고 충돌로 기록한다.

1. `result_received`: 기존 렌더러가 실제 받은 응답. 원문 근거와 시각 보존. 별도 추첨 요청 0회.
2. `overlay_finalized`: 해당 회차의 실제 선택 결과, 애니메이션 완료 경로, 현재 표시 항목, 가시 상태를 연결. 타임아웃·취소·강제 넘김은 구분하며 이 신호만으로 송출 완료를 주장하지 않음.
3. `program_evidence`: 시험 중 사용하는 방송 프로그램의 최종 출력과 대조. OBS 어댑터를 쓰는 시험에서는 프로그램 장면의 소스 포함·활성·변환 상태를 보조 근거로 사용. 다른 소스에 가림, 잘림, 필터, 중첩 장면, 전환을 검사. OBS API를 공통 수집기의 필수 의존으로 두지 않음.
4. 결과가 없는 공백은 원인과 마지막 정상 시각을 기록. 수신된 결과와 미표시 결과를 삭제하지 않고 별도 상태로 보존.

소스 활성 상태 또는 소스 단독 스크린샷은 최종 합성 화면에 보였다는 충분한 증거가 아니다. 자동 판정 범위와 실제 프로그램 출력 확인을 구분하며, 모든 시청자의 수신까지 보증하지 않는다. 관측기가 연결되기 전이나 끊긴 동안의 표시도 소급하여 확정하지 않는다.

원문·최소 필요한 화면 증거는 비공개 보관한다. 크기/보관 한도, 이벤트별 이유와 비교 필드, 재시작 경계, 누락 구간을 기록한다. 전체 해시만 남겨 원인을 잃는 과거 관측 문제를 반복하지 않는다.

## OBS 선택지를 시험할 경우의 순서와 공통 수락 조건

- 테스트 PC에서 기존 OBS 소스 하나에 연결해 원래 응답을 읽는다. 관측기 유무에 따라 위플랩 요청·추첨 횟수와 결과가 달라지지 않아야 한다.
- 단일 슬롯·원판·다회 추첨을 실제 프로그램 출력과 후원 UID/회차별로 대조한다. 봇 채팅을 보내지 않는 승인된 테스트에서도 수신되어야 한다.
- 숨김·장면 전환·취소·타임아웃·재생·소스 재로드·Agent 재시작·관측 단절을 시험한다. 중복 처리와 근거 없는 표시 성공 판정을 금지한다.
- 다른 계정/소스 격리, 비공개 증거, 부하, 소스 변경 감지와 미지원 버전의 수집 보류를 확인한 뒤 후보 배포를 판단한다.

원격 디버깅은 개발용 연결 방식이므로 그대로 일반 사용자용 완성 기능이라고 보지 않는다. 이 연결이 부적합하면 OBS 전용 관측 플러그인 또는 단일 렌더러를 Agent가 소유하는 구성을 비교한다. 후자는 영상·음성·투명도 전달과 기존 표시 경로 교체가 필요해 우선안보다 범위가 크다.

10월 9일 19시의 기존 URL 관측 예약은 후원·원문 수집 연구다. 위 관측기가 준비되기 전에는 방송 화면 결과 검증으로 계산하지 않는다. 예약·운영 수집·추첨 API·사용자 데이터 변경 없음.
