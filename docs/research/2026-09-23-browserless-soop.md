# SOOP 수집 확장성 검증 · 2026-09-23

## 판정과 목적

**브라우저 없는 수집의 기술적 가능성을 확인했다. 운영 교체·실제 500개 방송 수집 승인은 보류한다.** SDK 분리뿐 아니라 계정 담당자 할당과 전송 큐 처리량도 해결해야 한다.

기준은 서비스 2026.09.23.1, 소스 `a4d9a94a2275a61eeb2bfac45f935a7489b13b86`이다. 운영 코드·설정·DB 스키마·도메인·수집기 연결은 변경하지 않았다. 승인된 테스트 계정으로 조회만 수행했고 인증 토큰 갱신도 발생하지 않았다. 실험 도구는 운영 모듈에서 참조하지 않는다.

## 검증 방법

- 공식 SDK 원본을 수정하지 않았다. 재다운로드 SHA-256도 `4d6974d882013e4cae2797010668855d3c2aeb0d2a8f711b08f65578c118a016`로 일치했다.
- Node 24 예비 시험 후 NCP와 같은 **Node 22.23.2**에서 재검증했다. 부하 시험 PC는 Windows x64, Ryzen 7 9800X3D(16 논리 CPU)다. NCP의 Linux·2 CPU 조건은 재현하지 않았다.
- SDK가 인증 정보 조회 → 로그인/입장 프레임 → ready → 채팅·후원 callback으로 진행한다. HTTP 응답은 합성이고 WebSocket은 루프백이다. 외부 SOOP WebSocket 연결은 0개다.
- 한국어 채팅, 후원 수량, 방·발신자 식별자, 계정 혼선, callback 중복을 검사했다. 기능 시험에서는 현재 별록 분류 함수의 chat/donation 변환도 확인했다. 부하 시험은 callback 경계까지이며 DB·OBS까지가 아니다.
- 계정별 vm은 JS 상태 분리 수단이지 보안 경계가 아니다. 운영 후보에는 프로세스 격리와 네트워크 접근 제한도 필요하다.

## 발견한 제약

1. **공유 SDK 모듈은 계정 격리에 실패한다.** 하나의 realm에 두 계정을 넣자 같은 프레임이 양쪽 callback에 도달하고 방 정보도 섞였다. 계정별 realm에서는 혼선 0건이었다.
2. **종료된 SDK realm은 재사용할 수 없다.** 전역 emitter 파괴 뒤 callback 재등록이 TypeError로 실패했다. 재연결마다 새 realm을 생성한 시험은 통과했다.
3. **인증 실패의 최초 오류를 보존해야 한다.** 합성 401은 error callback 뒤 추가 TypeError를 일으켰다. 후보 어댑터는 인증·오프라인·일시 네트워크 실패를 구분하고 연결 시한을 강제해야 한다.
4. **수집 권한은 분산 잠금이 아니다.** 현재 권한 발급/검증 코드에 합성 DB·OAuth를 주입하면 같은 계정에 동시 요청한 두 워커가 모두 권한과 소유권 검사를 통과한다. 담당자를 기록하는 DB 쓰기는 0회다. 기존 계정·이벤트 소유권 검사는 유지하면서 원자적 담당자 할당·만료·갱신·이전 워커 차단을 추가해야 한다. 분산 인계 기능 자체는 이번에 구현하지 않았다.

## 실제 SOOP 조회 · 20:18 KST

NCP Node 22 프로세스에서 승인된 테스트 계정의 기존 수집 권한과 공식 SDK를 사용했다. 비밀값은 원격 프로세스 메모리에만 두고 출력·저장하지 않았다.

- 별록 권한 발급 HTTP 200, 토큰 갱신 없음.
- `POST /validate/live/status`: HTTP 200, result 1, `streamend`(방송 꺼짐).
- 이 오프라인 응답은 `user_id` 없이 `broad_no`에 계정 식별자를 넣었다. 기존 운영 코드의 대체 해석으로 연결 소유자 일치를 확인했다. 문서 필드만 가정하여 상태 감시기를 만들면 안 된다.
- SDK의 `POST /broad/access/chatinfo`: HTTP 200, result -1302, `invalid-chat-info`. 방송 꺼짐과 일치했다.
- 운영 테스트 채널은 전후 `waiting_for_live`, 대기 전송·실패 보관 각각 0건. 채팅 소켓을 열거나 수집기를 중단하지 않았다.

**방송 중 SDK ready·실제 후원·룰렛 수신·토큰 갱신·방송 종료 후 재시작은 미검증**이다. 시험 방송은 꺼져 있었으며 유료 후원을 임의로 보내지 않았다.

## 방송 대기 감시 분리

공식 문서에서 `validate_live_status` scope와 `POST /validate/live/status`를 확인했고 현재 테스트 계정 권한으로 성공했다. 기존 계정 연결 코드에서도 사용하는 API라, 브라우저 대신 대기 상태를 조회하는 후보는 타당하다.

앱/계정별 호출 할당량·동시 연결 제한 수치는 확인하지 못했다. 500대기 계정을 30초마다 조회하면 평균 16.7회/초, 60초마다면 8.3회/초라는 산술상 요청량이다. 허용량을 뜻하지 않는다. 지터·백오프·401/429 대응·시작 감지 지연을 검증해야 한다. 공개 방송 목록은 페이지당 최대 60개이므로 한 페이지에 없다고 오프라인으로 판단하면 안 된다.

## 전송 큐 병목

현재 암호화 outbox를 로컬 파일에 실행했다. 계정 100개·총 200건, 운영과 같은 병렬 전송 2개, 수신 API는 모의 지연 함수다.

| 모의 응답 지연 | 200건 배출 시간 | 처리율 | 최종 대기/실패 보관 |
|---:|---:|---:|---:|
| 100ms | 11.0초 | 18.2건/초 | 0 / 0 |
| 500ms | 51.2초 | 3.90건/초 | 0 / 0 |

중복 enqueue 억제, 파일 큐 재개방, 계정별 순서를 확인했다. 응답 유실 모의 시험은 전송 2회·수신측 적용 1회다. 수신측 중복 방지는 Set으로 모의했으므로 운영 DB 증거가 아니다. 프로세스 강제 종료 내구성 시험도 아니다.

예를 들어 500계정에서 수집 대상 이벤트가 계정당 분당 1건이면 총 8.3건/초다. 위 500ms 조건에서는 처리보다 유입이 많아 적체된다. 실제 이벤트율·API 지연을 측정하고 분산 큐·순서·중복 방지를 유지하며 전송량을 조정해야 한다. 무작정 병렬 수를 늘리면 DB 부하를 키울 수 있다.

## 동시 연결 시험 준비 · 20:39 KST

사용자가 테스트 계정에서 동시 연결을 확인한 뒤 관측계정A 방송에 관측 경로를 붙이는 순서를 승인했다. 재확인한 테스트 채널은 `waiting_for_live` / `broadcast_offline`이며 대기 전송·실패 보관·메모리 대기는 모두 0건이었다. 후보 연결은 시작하지 않았다. 시험 방송 시작을 사용자에게 요청했다.

## 테스트 방송 동시 수신 · 20:53–20:55 KST

위 준비 시점 이후 사용자가 시험 방송을 켰다. 기존 채널 `connected`, 실제 chatinfo의 소유자 일치를 확인한 뒤 후보를 실행했다.

- Node 22.23.2 기본 WebSocket 후보는 두 번 모두 ready 시한 10초를 넘겼다. 별도 전송 진단에서 DNS·TCP·TLS·HTTP Upgrade 101은 성공했으나 기본 WebSocket은 open에 도달하지 않았다. 정확한 구현 호환성 원인은 미확정이며 SOOP 서버 장애로 판정하지 않는다.
- SDK 원본을 유지하고 전송 구현만 기존 고정 의존성 `ws@8.21.0`으로 주입하자 ready와 실제 수신이 성공했다. 운영 의존성을 설치·변경하지 않았다.
- 후보는 별도 읽기 전용 컨테이너, 256 MiB, CPU 0.25, 프로세스 32개 제한, 권한 제거, 운영 볼륨·DB 키 없이 실행했다. 인증값은 원격 프로세스 파이프로만 전달했다. SDK 인증·입장·keepalive만 발신했다.
- 90초 후보 관측 동안 사용자가 보낸 실제 채팅 2건을 수신했다. 기존 브라우저의 읽기 전용 CDP 관측 프레임과 같은 무작위 키로 HMAC을 계산하여 **2건 일치, 한쪽에만 존재하는 프레임 각각 0건**을 확인했다. 원문·아이디는 결과에 기록하지 않았다.
- 기존 연결의 종료 이벤트와 상태를 함께 감시했다. 약 115초 감시 전후 `connected`, 전송 대기·실패 보관 모두 0건, 중단 조건 발생 없음. 후보는 시한 종료 후 제거 확인했다.

이 결과는 **동일 테스트 계정의 짧은 동시 연결과 실제 채팅 수신**의 증거다. 후원·룰렛·재연결 공백·토큰 갱신·장시간 격리 안정성·500개 실제 연결은 검증하지 않았다. 운영 이벤트 전송 및 DB 쓰기는 기존 수집기만 담당했다. 비공개 실행 증거는 `coexist-result.jsonl`, `coexist-native-diagnosed.jsonl`, `transport-result.jsonl`이다.

| 확인 항목 | 결과 |
|---|---|
| 후보 SDK ready | 성공 |
| 실제 채팅 프레임 | 기존 8건 / 후보 8건 |

로그인·입장·keepalive 외 후보 발신은 없었다. 기존 수집기만 운영 이벤트 전송과 데이터 반영을 담당했다. SDK에서 채팅 8건 외 입장·퇴장·초기 상태 callback을 포함해 총 16건을 수신했으나, 초기 상태 callback 수는 전달 경로 동등성의 근거로 사용하지 않았다. 비교 시 시작·종료 경계는 각 1초 제외했다.

관측 구간에 실제 후원·룰렛 결과는 수신되지 않았다. 따라서 **브라우저 없는 실제 인증·입장·채팅 수신 및 두 경로의 단기 공존까지 확인**했으며, 후원 처리 동등성·장기 안정성·500명 수용 가능을 확정하지 않는다. 자동 재연결·장애 인계는 이번 실방송에서 유도하지 않았다. 운영 배포·수집기 교체·재시작은 하지 않았다.
