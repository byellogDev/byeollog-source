# 배포 후보 사전 코드 리뷰 · 2026-09-24

> 후속 수정: 아래 4건의 재현 조건을 회귀 검사로 추가하고 코드를 수정했습니다. 운영 DB·보호된 앱 후보·예약 연구 코드의 반영 범위와 수집 런타임 추가 승인 대기는 [수정 릴리스 기록](../releases/2026-09-24-candidate-review-fixes.md)에 구분했습니다. 아래 내용은 **수정 전 리뷰 당시의 증거**입니다.

## 판정

**수정이 필요한 결함 4건을 확인했습니다. 두 후보의 운영 채택 판정은 보류합니다.** 이번 작업은 리뷰와 로컬 재현이며, 운영 코드·권한·데이터·배포·관측 예약을 변경하지 않았습니다. 사고가 실제로 발생했다는 판정과 코드상 재현을 구분합니다.

대상은 마크 연동 보호 후보의 프록시·콜백·저장소·발급 도구·관련 SQL과 SDK 없는 WebSocket 후보의 프로토콜·클라이언트·관측기·감독기·비교기입니다. 기존 수집기의 lease 발급 경로도 호출 관계를 따라 검토했습니다. 수집 후보의 재생성 bundle 6개 해시는 예약 receipt와 모두 일치했습니다. 마크 후보는 앞서 배포 소스 일치를 확인한 4개 수정 파일과 그 의존 코드를 대상으로 했습니다.

## R1 · P1 · 정지한 게임 연결이 재연동으로 활성화됨

- 위치: `apps/admin-runtime/lib/game-link-service.mjs:205`, `supabase/migrations/20260921190000_add_game_identity_linking.sql:163-173`.
- 기존 활성 연결만 찾아 Microsoft 인증을 생략합니다. `suspended` 연결은 그 검사에서 빠져 신규 인증 단계로 진행하며, 완료 RPC가 같은 SOOP·Minecraft 조합의 기존 연결을 무조건 `active`로 바꿉니다.
- 관리자 정지를 사용자가 자신의 두 계정을 다시 인증하는 것으로 해제할 수 있습니다. 서버 grant가 그대로 active라면 정지로 막았던 신원 조회도 다시 허용될 수 있습니다.
- 확인: 메모리 저장소에서 같은 신원의 `suspended → completeSession → active`를 재현했습니다. 실제 운영 DB의 함수 정의도 읽기 전용으로 확인했으며 `suspended` 방어 없이 `status = 'active'` 갱신이 존재합니다. 실사용 연결의 상태를 바꾸지는 않았습니다.
- 유입: 이번 후보가 새로 추가한 분기는 아니며 인계된 기존 SQL·저장소 동작입니다. 후보도 같은 DB 함수를 사용합니다.
- 수정 조건: 최종 완료 RPC의 잠금 구간에서 정지 상태를 거절하고, 관리자 해제 절차와 분리합니다. 기존 적용 migration을 고쳐 재실행하지 말고 후속 migration으로 처리합니다. 메모리·실제 DB 롤백 검사에서 정지 상태와 기존 grant가 유지되는지 확인해야 합니다.

## R2 · P1 · 읽기 전용 관측 준비가 운영 토큰을 갱신할 수 있음

- 위치: `tools/soop-direct-lab/soak-monitor.mjs:21-26`, `apps/collector-runtime/lib/soop-gateway-api.js:74`, `apps/collector-runtime/lib/soop-oauth.js:295-326`.
- 관측기는 `kind: lease`로 인증정보를 요청하고 응답의 `refreshed`가 true면 중단합니다. 하지만 lease 처리기는 이미 남은 토큰 시간이 120초 이하일 때 공급자 갱신과 DB PATCH를 수행한 뒤 그 응답을 보냅니다.
- 따라서 사후 `lease.refreshed` 검사는 관측기의 운영 인증정보 변경을 방지하지 못합니다. 운영 수집기의 자체 갱신과 경합할 수 있으며, 갱신 실패 시 연결 오류·재인증 필요 상태를 기록하는 분기까지 도달할 수 있습니다. 이번 리뷰로 실제 운영 단절이 발생했다고 단정하지 않습니다.
- 확인: 실제 gateway handler와 refresh 함수를 사용하고 외부 HTTP·DB만 메모리 대역으로 교체했습니다. 만료 90초 전 입력에서 공급자 갱신 1회, DB PATCH 1회, `refreshed: true` 반환을 재현했습니다. 실제 공급자·운영 DB에는 요청하지 않았습니다.
- 유입: 기존 SDK 관측 방식에서도 사용하던 준비 경로가 직접 연결 후보에 남아 있습니다. 직접 WebSocket 수신기 자체는 갱신하지 않지만 전체 관측 시스템은 순수 읽기 전용이 아닙니다.
- 수정 조건: 갱신하지 않는 별도 관측용 자격 조회 계약을 사용합니다. 만료 임박 시 관측만 대기하고 운영 수집기가 갱신한 값을 이후 다시 읽어야 합니다. 클라이언트에서 미리 만료 시각을 확인하는 것만으로는 조회 사이 경합을 막을 수 없습니다.

## R3 · P2 · 남은 게임 쿠키가 일반 SOOP 가입/연결 콜백을 막음

- 위치: `apps/admin-runtime/lib/soop-oauth.js:521-523`.
- 일반 별록 OAuth 시도가 유효하고, 이전 게임 연동 쿠키가 남아 있으며, 공급자 콜백에 state가 없으면 인증코드 처리 전 400을 반환합니다. 일반 흐름 자체는 state 미반환 콜백을 처리하는 분기가 있는데, 새 공통 분기는 게임 세션이 DB에서 유효한지 확인하지 않고 쿠키 형식만으로 차단합니다.
- 시작 핸들러는 게임 쿠키를 정리하지 않으며 이 실패 응답도 쿠키를 지우지 않습니다. 게임 연동 중단 후 일반 가입·SOOP 연결을 시도할 때 쿠키 유효기간 동안 반복 실패할 수 있습니다. state가 정상 반환되는 경우에는 이 조건이 성립하지 않습니다.
- 확인: 같은 유효 일반 시도·같은 state 없는 콜백에 게임 쿠키 유무만 바꿨습니다. 쿠키가 없으면 mock 인증코드 교환까지 진입하고, 있으면 교환 0회·400·게임 쿠키 미정리로 끝났습니다. mock 공급자는 의도적으로 거절 응답을 반환하므로 이 재현은 정상 가입 완료를 주장하지 않습니다.
- 유입: 이번 후보에서 모호한 콜백을 거절하도록 추가한 분기의 사용자 흐름 회귀입니다. 기존 자동검사는 400 거절만 기대하므로 사용자가 다시 정상 흐름으로 진행할 수 있는지는 검출하지 못합니다.
- 수정 조건: 일반/게임 인증 시작 단계부터 활성 흐름을 명확히 선택하고 모호한 상태를 안전하게 해소합니다. state 검증을 느슨하게 만드는 해결은 사용하지 않습니다. 이전 게임 쿠키·만료 세션·state 유무·동시 탭·취소 후 재시도를 조합해 검사합니다.

## R4 · P2 · 종료 직전 불일치가 정상 종료 사유로 남음

- 위치: `tools/soop-direct-lab/soak-controller.py:150-165,185-187,206-209`.
- 실행 중에는 `comparison.mismatched()`를 검사하지만, 종료 시 `finally`의 마지막 expire에서 새로 드러난 불일치는 report에만 넣고 reason을 변경하지 않습니다. campaign은 `campaign_complete`면 바로 종료하고 `duration_reached`면 다음 관측으로 넘어갑니다.
- 종료 직전 한쪽에서만 받은 후원이 최종 집계에 남아도 `needs_review`로 승격되지 않을 수 있습니다. 종료 경계의 대조 미완료를 성공으로 해석하거나 경고를 놓칠 위험이 있습니다.
- 확인: 원본 controller/compare 파일의 비공개 사본을 사용하고 시계·프로세스·입출력을 대역으로 교체했습니다. 후원 코드 18이 기존 경로에만 1건 존재한 상태에서 `monitor_done`을 주면 최종 `only.original = {18: 1}`인데 reason은 `campaign_complete`로 반환됐습니다. 실제 Docker·SSH·수집기는 실행하지 않았습니다.
- 수정 조건: 종료 시 양쪽의 남은 큐를 제한된 시간 동안 처리하고 공통 관측 구간을 확정합니다. 최종 불일치는 종료 사유보다 우선해 검토 대상으로 전달하고, 비교 불가능한 꼬리 구간은 성공 대신 대조 공백으로 집계합니다.

## 별도 남은 작업

이미 기록한 분산 요청 제한, 세션/nonce/audit 정리, 실제 OAuth 흐름, 운영 주소로 구성한 승격 후보 검증은 여전히 필요합니다. 후원→마크 전달 모듈은 아직 미구현이며 이번 신원 조회 후보에 해당 전달 기능이 포함됐다고 보지 않습니다. WebSocket 후보는 수신 전용 연구 코드이므로 운영 전송 큐·ACK·멱등키·장애 인계까지 검증한 것으로 확대하지 않습니다.

우선순위는 관측 준비의 운영 토큰 변경 경로 제거와 정지 연동 재활성화 차단입니다. 이후 일반 OAuth 흐름 분리와 최종 불일치 판정을 수정하고 해당 재현을 회귀 테스트로 전환해야 합니다. 관측기 수정 전후 결과는 코드 해시와 구간을 분리해야 하며, 기존 48시간 예약·증거를 덮어쓰지 않습니다.
