# 개발과 버전 기록

1. `main`의 최신 릴리스에서 작업 브랜치를 만듭니다.
2. 대상 기능의 소유 앱과 권한 경계를 확인합니다.
3. 변경·검사 결과·미확인 항목을 PR에 기록합니다. 소스 해시 변경은 manifest에 명시합니다.
4. CI, 게시 전 검사, 변경에 필요한 사용자 흐름을 확인합니다.
5. 운영 담당 작업 공간에서 검증한 후보만 승격합니다.
6. `CHANGELOG.md`와 `docs/releases/날짜.md`를 갱신하고 버전 태그를 남깁니다.

기능 작업 공간의 구현 완료는 운영 반영 완료를 의미하지 않습니다. 해당 작업은 커밋·diff·테스트 결과·배포 필요 파일을 전달하고, 운영 작업 공간에서 현재 운영 기준과 비교합니다.

## 검사 종류를 구분하기

| 분류 | 증명하는 범위 |
| --- | --- |
| 소스·해시 대조 | 원본이 의도하지 않게 바뀌었는지 |
| 단위·계약 검사 | 입력과 기대 동작, 오류·권한 처리 |
| 후보 응답 비교 | 실제 배포의 상태·본문·자산 일치 |
| 실제 계정 흐름 | 로그인부터 API·데이터·화면까지 실제 실행 |
| 사용자 확인 | 실제 방송·OBS 등 사용 환경의 확인 |

한 분류의 통과를 다른 분류의 완료로 대신하지 않습니다. 특히 `401` 응답 확인은 접근 차단 검사이며, 로그인한 사용자의 기능 완료 검사가 아닙니다.

## GitHub 기록 규칙

2026-09-24 사용자 결정에 따라 **주요 작업 완료마다 커밋·push하고, 최소 하루 한 번 기록 누락을 점검**합니다. 일일 점검은 한국 시간 오후 11시에 실행합니다. 변경이 없으면 빈 커밋과 반복 알림은 만들지 않습니다.

- `docs/work-log/YYYY-MM-DD.md`에 목적, 해결한 문제, 변경, 실제 실행한 검사, 미검증, 운영 반영 여부, 커밋·PR 또는 릴리스 문서 링크를 남깁니다.
- 기존 완료 작업은 실제 변경 목록으로 선택해 커밋하고 원격 SHA를 확인합니다. 연구·미완성 코드는 상태를 명시하며 진행 중인 다른 작업을 임의로 완성본에 묶지 않습니다.
- 게시할 Git 파일 목록을 기준으로 `node tools/scan-publication.mjs --tracked`와 staged diff를 검사합니다. 비공개 저장소라도 인증값과 회원 정보는 넣지 않습니다.
- `codex/` 작업 브랜치와 PR로 변경을 남깁니다. 일일 기록 자동화는 자동 merge나 운영 배포를 수행하지 않습니다.
- 자동화는 새 업로드 또는 조치가 필요한 실패만 알립니다. 검사 실패·민감정보 탐지·원격 충돌은 숨기거나 검사를 우회하지 않습니다.

모든 버전은 목적, 이전 문제, 변경 내용, 검증 근거, 영향, 복구 방법을 기록합니다. 개인 식별자·연결 토큰·로그 원문·서버 접근 정보를 공개 문서에 넣지 않습니다. 포트폴리오에는 본인이 판단한 설계와 검증 사실을 구분하고 측정하지 않은 개선율을 작성하지 않습니다.

원격 저장소 push는 운영 배포를 자동 실행하지 않습니다. CI도 운영 자격증명 없이 빌드·검사만 수행합니다.
