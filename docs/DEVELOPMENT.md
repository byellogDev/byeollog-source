# 개발과 버전 기록

1. `git fetch origin` 후 `origin/main`에서 목적별 작업 브랜치를 만듭니다. 운영 재현은 구성요소의 정확한 릴리스 태그를 별도로 사용합니다.
2. 대상 기능의 소유 앱과 권한 경계를 확인합니다.
3. 변경·검사 결과·미확인 항목을 PR에 기록합니다. 소스 해시 변경은 manifest에 명시합니다.
4. CI, 게시 전 검사, 변경에 필요한 사용자 흐름을 확인합니다.
5. 운영 담당 작업 공간에서 검증한 후보만 승격합니다.
6. 주요 작업·버전마다 `docs/templates/release.md`로 `docs/releases/YYYY-MM-DD-topic.md`를 작성하고 릴리스 목록과 `CHANGELOG.md`를 갱신합니다. 정식 버전 발행 시 해당 커밋에 버전 태그를 남깁니다.

기능 작업 공간의 구현 완료는 운영 반영 완료를 의미하지 않습니다. 해당 작업은 커밋·diff·테스트 결과·배포 필요 파일을 전달하고, 운영 작업 공간에서 현재 운영 기준과 비교합니다.

## 검사 종류를 구분하기

| 분류 | 증명하는 범위 |
| --- | --- |
| 소스·해시 대조 | 원본이 의도하지 않게 바뀌었는지 |
| 단위·계약 검사 | 입력과 기대 동작, 오류·권한 처리 |
| 후보 응답 비교 | 실제 배포의 상태·본문·자산 일치 |
| 실제 계정 흐름 | 로그인부터 API·데이터·화면까지 실제 실행 |
| 사용자 확인 | 실제 방송·OBS 등 사용 환경의 확인 |

한 분류의 통과를 다른 분류의 완료로 대신하지 않습니다. 특히 `401` 응답 확인은 접근 차단 검사이며, 로그인한 사용자의 기능 완료 검사가 아닙니다.

## GitHub 기록 규칙

2026-09-24 사용자 결정에 따라 **주요 작업 완료마다 커밋·push하고, 최소 하루 한 번 기록 누락을 점검**합니다. 일일 점검의 원래 예정 시각은 한국 시간 오후 11시였으나, 예약은 이후 사용자 요청으로 중지했습니다. 새 작업에서 예약이 활성 상태라고 가정하거나 임의 재개하지 않습니다. 변경이 없으면 빈 커밋과 반복 알림은 만들지 않습니다.

- `docs/work-log/YYYY-MM-DD.md`에 목적, 해결한 문제, 변경, 실제 실행한 검사, 미검증, 운영 반영 여부, 커밋·PR 또는 릴리스 문서 링크를 남깁니다.
- **릴리스 문서는 필수이며 일일 작업 기록으로 대체하지 않습니다.** 목적·변경 전 문제·구성요소별 변경·검증과 미검증·사용자 영향·복구·관련 커밋/PR을 작성하고 [릴리스 목록](releases/README.md)에 연결합니다. 후보·연구·운영 반영 상태와 확인 시각을 구분하고, 후속 반영은 이전 기록에 최신 문서 링크를 추가합니다. 일일 점검에서도 문서와 링크 누락을 확인합니다.
- 기존 완료 작업은 실제 변경 목록으로 선택해 커밋하고 원격 SHA를 확인합니다. 연구·미완성 코드는 상태를 명시하며 진행 중인 다른 작업을 임의로 완성본에 묶지 않습니다.
- 게시할 Git 파일 목록을 기준으로 `node tools/scan-publication.mjs --tracked`와 staged diff를 검사합니다. 비공개 저장소라도 인증값과 회원 정보는 넣지 않습니다.
- `codex/` 작업 브랜치와 PR로 변경을 남깁니다. 일일 기록 자동화는 자동 merge나 운영 배포를 수행하지 않습니다.
- 자동화는 새 업로드 또는 조치가 필요한 실패만 알립니다. 검사 실패·민감정보 탐지·원격 충돌은 숨기거나 검사를 우회하지 않습니다.

모든 버전은 목적, 이전 문제, 변경 내용, 검증 근거, 영향, 복구 방법을 기록합니다. 개인 식별자·연결 토큰·로그 원문·서버 접근 정보를 공개 문서에 넣지 않습니다. 설계 판단과 실제 검증 결과를 구분하고 측정하지 않은 개선율을 작성하지 않습니다.

원격 저장소 push는 운영 배포를 자동 실행하지 않습니다. CI도 운영 자격증명 없이 빌드·검사만 수행합니다.

## GitHub Releases 게시 완료 기준

- 정식 버전·주요 작업의 공개 기록은 본 저장소 `byellogDev/byeollog`의 [Releases](https://github.com/byellogDev/byeollog/releases)에도 게시합니다. 문서 커밋·태그·별도 바이너리 저장소 게시만으로 완료라고 보고하지 않습니다.
- 기존 릴리스가 있으면 내용과 태그를 확인해 중복을 피합니다. 새 기록은 검증한 실제 커밋에 연결하며 기존 태그를 이동하지 않습니다. 날짜별 기록에 여러 구성요소가 있으면 각각의 운영·후보·연구 상태를 구분합니다.
- 연구 전용 체크포인트는 prerelease로, 최신 정식 버전만 Latest로 지정합니다. 과거 기록 보완은 실제 작업일과 게시일을 구분합니다.
- 본문에는 목적·변경·검증·미검증·사용자 영향·복구 문서·소스 커밋·PR·설치 파일 저장소를 연결합니다. 문서 링크는 실제 원격에 있는 커밋으로 고정해 기본 브랜치에 없는 문서의 링크가 깨지지 않게 합니다.
- 게시 후 GitHub API에서 본문, draft=false, prerelease 여부, 태그 커밋, Latest를 다시 읽어 확인합니다. 최종 응답에는 본 저장소의 실제 Release URL을 제공합니다.
- 문서가 작업 브랜치에만 있으면 그 상태를 정확히 밝힙니다. 기록을 보이게 하려고 미완료 기능을 기본 브랜치에 자동 병합하지 않습니다.
