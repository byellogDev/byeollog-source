# 별록 연속 룰렛·다중 아봉 후속 분석

작성일: 2026-08-22
상태: 분석 보존, 이번 실후원 지연 수정 범위에서는 구현하지 않음

## 사용자가 확정한 기대 동작

- 한 후원의 연속 룰렛에서 `아봉 10초`가 2개 나오면 총 20초를 적용한다.
- 첫 아봉이 시작되고 5초 뒤 두 번째 아봉이 도착하면 첫 시작부터 총 20초,
  즉 두 번째 도착 후 15초 뒤에 마이크와 오버레이를 함께 해제한다.
- 중간에 마이크가 복원되거나 오버레이가 사라졌다 다시 나타나는 깜빡임이 없어야 한다.

## 현재 구현

1. 위플랩 결과 문자열은 `&`만을 구분자로 사용하고 각 조각의 앞뒤 공백을 제거한다.
2. 한 원본 후원에서 donation 이벤트 1개와 룰렛 결과별 roulette 이벤트 N개를 만든다.
3. 각 roulette 이벤트는 독립적으로 규칙 평가와 실행 큐 생성을 거친다.
4. 같은 PC·같은 마이크 대상의 시간제 음소거 실행이 겹치면 Local Agent가 활성
   세션에 요청 시간을 더한다.
5. 오버레이도 같은 방식으로 표시 시간을 더하며 마지막 요청의 이미지·위치를 적용한다.
6. 한 연속 세션의 안전 상한은 900초(15분)다.

## 현재 구조의 한계

- 룰렛 묶음을 서버에서 먼저 합산해 하나의 실행으로 만드는 구조가 아니다.
- 두 번째 실행이 첫 번째 종료 후에 도착하면 하나의 20초 세션이 아니라 10초 세션
  두 번으로 실행될 수 있다.
- 중간 네트워크 실패·재시도·claim 지연이 있으면 원본 묶음의 모든 결과가 같은 물리
  세션에 합류한다는 원자적 보장이 없다.
- 서로 다른 이미지가 매칭되면 현재는 마지막 도착 이미지로 교체된다. 이미지별 표시
  정책은 제품 결정이 필요하다.
- 개별 execution ACK는 각 요청의 10초를 보존하지만 실제 물리 세션의 합산 시간과
  묶음 단위 결과를 한눈에 설명하지 못한다.

## 다음 구현 권고

1. `sourceUid + correlationId`를 원본 후원 묶음 ID로 고정한다.
2. 한 원본의 룰렛 결과 배열을 서버에서 한 번에 수신·저장한다.
3. 규칙 평가 결과를 `device + action type + microphone target + overlay policy`로 묶는다.
4. 같은 액션의 횟수와 시간을 트랜잭션 안에서 합산한다.
   - 예: `아봉 10초 × 2` → `durationMs=20000`, `matchCount=2`
5. idempotency key에 원본 묶음 ID, 규칙 버전, 합산 그룹을 포함한다.
6. 이미 실행 중인 세션에 늦은 결과가 추가될 경우 DB와 Agent가 동일한 누적 마감
   시각을 공유하는 durable extension 계약을 둔다.
7. 실행 기록 UI에는 원본 결과 수, 매칭 수, 합산 시간, 실제 시작·종료 시각을 표시한다.

## 필수 회귀 시험

- 동시에 `아봉 10초` 2개 → 20초 동안 한 번만 잠금·한 번만 복원
- 두 번째가 5초 뒤 도착 → 두 번째 도착 후 15초 뒤 복원
- 10연속 룰렛에서 아봉 0/1/2/10개
- 동일 원본 재전송·부분 HTTP 실패·execution redelivery에서 시간 중복 추가 금지
- Agent 재시작 중 누적 세션 복구
- 서로 다른 이미지·OBS/Windows 마이크 대상 혼합 시 확정된 정책대로 동작
- 15분 안전 상한 초과 시 사용자에게 명확한 실패 표시

## 이번 지연 수정과의 경계

이번 수정은 위플랩 결과 감지 주기 단축, 신규 행 즉시 이벤트 전송, 실행 생성 직후
Local Agent 깨우기, 단계별 지연 로그 추가만 수행한다. 위 다중 아봉 합산 계약과 서버
스키마/Runtime 변경은 크레딧 보충 후 별도 작업으로 진행한다.
