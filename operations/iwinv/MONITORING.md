21:21 KST 후속 배포에서 Discord 알림에 미허용 포트·원인 판정 한계·확인 조치를 추가했다. `patch-alert-details.py`는 바로 앞의 감시 보완이 설치된 파일에 적용하며 `deploy-alert-details.py`로 후보 검증·원자 교체한다. 그 이전 감시로 복구할 때는 상세 알림 변경을 먼저 되돌린다. [상세 기록](../../docs/releases/2026-10-14-discord-connection-details.md).

## 포트 근거와 허용 범위

실제 채팅 TLS 연결에서 확인한 포트는 **8041, 9001**이다. 목적지 IP는 재접속마다 변경될 수 있다. 현재 승인된 TCP 출발 포트는 53/80/443/8041/9001, UDP는 53/123이며 인바운드 SSH 제한은 별도 유지한다.

[SOOP 공식 SDK](https://static.sooplive.com/asset/app/chat-sdk/sooplive-chat-sdk.js)는 API의 `chat_ip`, `chat_port`를 받아 TLS 접속 시 **포트 + 1**을 사용한다. [공식 연결 문서](https://developers.sooplive.com/docs/chatsdk/connection)와 SDK에서 공급자가 앞으로 사용할 전체 포트 범위는 확인하지 못했다. 8041·9001이 영구적인 전체 목록이라는 뜻이 아니다.

2026-10-14 확인 자료 SHA-256:

- SDK: `8f89b163d29ddf885dd3de9cddba98b8446fe26c8b3d96483644f4acb47254a5`
- 공식 문서의 chatsdk 번들: `712d1f72b270c1e4de4eee04fd4edf0492897605e514a5a57c420d9e650e4f06`

`egress-policy.json`은 승인된 방화벽 정책의 대조 기준이다. 감시가 클라우드 규칙을 자동으로 조회하거나 변경하지 않는다. 새로운 포트 경고 시 실제 SOOP 할당과 차단 여부를 확인하고 승인 범위로 방화벽을 적용한 뒤 이 정책을 함께 갱신한다. 넓은 임의 범위나 모든 포트를 열지 않는다.

## 실패·복구 판정

- `infra-health.py`는 30초 주기로 로컬 worker 상태와 수집 컨테이너 네트워크 소켓을 읽는다. DB·웹·Discord 조회 주기는 기존 운영 모니터의 약 2분을 유지한다.
- 연결 실패를 상태 파일에 기억한다. 뒤이어 `connecting`이나 빈 오류 필드가 나와도 해제하지 않는다. 새 연결의 첫 대기는 최대 90초만 허용한다.
- 60초 이내 worker 상태에서 `connected`와 오류 없음, 또는 `waiting_for_live`와 `broadcast_offline`이 확인돼야 채널 복구 증거로 사용한다. 실패한 채널이 목록에서 사라지면 검토할 때까지 오류를 유지한다.
- 운영 모니터는 서로 다른 신선한 health 기록 두 개로 경고·복구를 판정한다. 재시도·불명 상태는 복구 연속 횟수를 초기화하고 잘못 대기 중인 복구 알림을 취소한다. health 기록이 90초를 넘으면 상태 점검 중단으로 처리한다.
- TCP `ESTAB`/`SYN-SENT`에서 승인 목록 밖의 공인 목적지 포트를 찾으면 번호만 저장하고 별도 경고한다. 소켓이 사라져도 기록을 유지하며 승인 정책에 반영된 경우에만 해당 번호를 해제한다. 소켓 조회 실패도 별도 경고 대상이다.

30초는 상태 관측 간격이다. 알림은 약 2분 주기의 두 관측, 기존 경고 재알림 제한·전송 재시도에 영향을 받으므로 30초 내 통지를 보장하지 않는다. 짧은 소켓 시도는 샘플링 사이에 끝날 수 있지만 연결 오류 감시는 별도로 계속된다. 공급자의 새 포트·외부 장애를 사전에 완전히 막는 보장은 없다.

## 배포·복구

정식 Git 소스의 파일만 보호된 후보 디렉터리로 전송하고 `deploy-health.py prepare`로 검증한다. 현재 설치 파일의 정확한 해시가 다르면 중단한다. 운영 모니터는 `patch-ops-monitor.py`가 지정한 구문만 한 번씩 수정하며 패턴 불일치·중복 적용은 거부한다.

후보는 회귀 검사 및 실제 호스트 입력을 사용하되 별도 상태 디렉터리에 기록한다. `install`은 감시 타이머만 잠시 멈추고 진행 중인 점검이 끝난 뒤 검증한 파일을 원자 교체한다. 수집 컨테이너 ID·이미지·시작 시각·재시작 횟수 불변과 설치 해시를 확인한다. 기존 알림 DB·인증 설정·후원 큐는 보존한다.

실패하면 보호된 이전 파일·모드·타이머 설정으로 복구하고 타이머를 다시 시작한다. 필요 시 같은 후보의 `deploy-health.py rollback`을 사용한다. 설치 이후 파일이 다른 버전으로 바뀌었으면 덮어쓰지 않고 중단한다. 새로 생긴 채널 감시 상태는 롤백 후 이전 감시에서 사용하지 않으며 증거로 보존한다. 운영 실패 상태나 누락 기록을 정상 판정을 위해 임의 삭제하지 않는다.

검사:

```sh
node --test tests/iwinv-health.test.mjs
python3 -B operations/iwinv/monitor-recovery.test.py /usr/local/sbin/byeollog-ops-monitor
```

두 번째 명령은 **수정 전 모니터**를 대상으로 회귀를 재현한다. 수정 후 파일은 중복 패치 방지로 거부한다. 시험은 함수만 분리해 호출하며 실제 경고를 보내거나 운영 데이터를 변경하지 않는다.
