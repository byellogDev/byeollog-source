# iwinv 운영·이전 절차

2026-10-05 06:20 KST부터 KR1-Z03의 단독형 2vCPU/8GB/NVMe 50GB, Ubuntu 24.04가 운영 수집 호스트다. 06:30 재부팅 뒤 운영 수집·6개 타이머·연구 재개를 확인했다. 기존 NCP VM은 정지했고 원본 디스크를 보존한다. [운영 이전 결과](../../docs/releases/2026-10-05-iwinv-migration.md)와 이전 단계의 [후보 릴리스](../../docs/releases/2026-10-05-iwinv-candidate.md)를 구분한다.

## 현재 운영 기준

- 2026-10-05 19:25 SDK 계정 접미사 수정 이미지로 교체하고 연구 v6를 새 구간에서 시작했다. 이전 시점의 동일 이미지 설명은 이전 완료 당시의 기록이다. [장애 원인·수정·검증·복구](../../docs/releases/2026-10-05-room-owner-suffix.md).

- 기존 Chromium/SDK 경로만 운영에 반영한다. 직접 WebSocket 후보는 동일 호스트에서 격리된 수신 전용 관측을 계속한다.
- 수집 컨테이너의 이미지·환경변수는 이전 전과 동일하다. 상태 포트는 호스트 loopback에만 바인딩하고 외부 서비스 포트를 공개하지 않는다.
- SOOP 실연결 기록에서 확인한 TCP 9001을 출발 통신에 추가했다. 공급자가 다른 포트를 할당할 경우 실제 응답을 근거로 규칙을 갱신한다. 전체 포트/IP 양방향 허용은 사용하지 않는다.
- 백업 전용 사용자의 숫자 UID가 이전 호스트와 달라 보관 파일 소유권을 새 사용자에 맞췄다. 백업·보관 정리는 공유 잠금을 사용하므로 동시에 수동 실행하지 않는다.
- 연구는 영구 systemd unit으로 등록했다. `research-resume-guard.py`가 `needs_review`, 손상되거나 과도하게 큰 증거 파일을 발견하면 부팅 시 시작을 막는다. 자동 Restart는 사용하지 않는다. 문제가 있는 구간을 삭제해서 시작 조건을 우회하지 않는다.
- 비공개 campaign receipt와 조회 도구의 대상 호스트도 변경했다. 이전 자료는 별도 구간으로 보존하며 정지·방송 대기를 수집 성공 시간으로 집계하지 않는다.
- 이전 NCP는 컨테이너 restart policy가 `no`, 6개 타이머가 disabled인 상태다. 복구 시 새 호스트의 쓰기를 먼저 멈추고 최신 큐를 대조한 뒤에만 이전 작업을 명시적으로 재개한다.
- 이전 전부터 발생한 백업 보관 정리 HTTP 500은 별도 미해결 항목이다. 독립 암호화 백업 성공과 보관 정리 성공을 혼동하지 않는다.

## 후보 준비

- 전용 SSH 키를 사용하고 비밀키·호스트 주소·공급자 식별자는 비공개 운영 기록에만 둔다. 관리 PC의 IP가 바뀌면 접속 허용 규칙을 의도적으로 갱신한다.
- 클라우드 방화벽과 OS 방화벽을 함께 사용한다. 관리 IP의 TCP 22만 외부 인입을 허용하며 비밀번호 로그인을 차단한다. 공개 HTTP·Docker API·수집기 상태 포트를 열지 않는다.
- 설치용 외부 통신 규칙은 TCP 80/443/53, UDP 53/123이다. 실제 SOOP 연결 목적지/포트는 운영 전환 전에 따로 대조한다. ELCAP의 ALL TCP/UDP 규칙은 양방향 허용 위험이 있으므로 사용하지 않는다.
- 현재 운영 중인 컨테이너의 **이미지 ID**를 기준으로 이미지 자체만 스트리밍 복사한다. 운영 환경변수나 볼륨을 테스트에 섞지 않는다. 복사 후 ID 일치와 기존 운영 컨테이너의 ID·이미지·기동 시각 불변을 확인한다.
- 동일 이미지에서 `tools/verify-soop-browser-lifecycle.mjs`와 `operations/ncp/probe-browser-capacity.mjs`를 실행한다. 임시 컨테이너는 공개 포트·운영 볼륨 없이 메모리/PID/CPU 상한, read-only, cap-drop을 적용하고 종료 후 회수를 확인한다.

## 전환 전 인벤토리

Docker 하나만 이전해서는 안 된다. 다음 구성의 실행 파일, unit 정의, 비공개 설정, 상태 디렉터리, 소유권과 백업 위치를 각각 대조한다.

1. 기존 SDK 수집기: 검증한 이미지·compose, 암호화된 전송 큐, 암호화 키, 인증 범위, 수집 담당 계정.
2. 호스트 타이머 6개: 디스크 정리, 수집기 건강 확인, 독립 암호화 백업, 운영 모니터, 업보 재시도, 풍벽지 백업 보관 정책.
3. 진행 중인 직접 WebSocket 연구 관측기: 현재 감독자와 계정별 후보, 원문 진단·집계, 실행 receipt와 관측 구간. transient unit은 VM 재부팅 뒤 자동 복구되지 않으므로 재개 정의를 별도로 준비한다.
4. 실패한 과거 SDK 연구 unit은 활성 서비스에 포함하거나 재시작하지 않는다.

## 전환 순서와 판정

1. 실제 SOOP 도달성·인증·계정 격리와 해당 공급자에서의 연결 연속성을 확인한다. 합성 SDK 시험을 실방송 수신 성공으로 계산하지 않는다.
2. 기존 방송 상태와 미전송·실패 큐를 확인하고 전환 가능한 시점을 정한다. 큐가 남으면 먼저 처리하거나 암호화 상태와 키를 함께 보존해 복구한다.
3. 이미지·설정·볼륨·연구 자료를 보존하고 이전 컨테이너와 타이머/연구의 종료 시각을 기록한다.
4. 이전 운영 수집과 중복 쓰기 작업을 정지한 뒤 새 서버의 운영 수집과 타이머를 시작한다. 새 프로세스는 instanceId를 새로 만들므로 lease만 믿고 두 운영 수집기를 동시에 실행하지 않는다.
5. 계정별 후원 전달, 누락·중복, 재시도, 백업 성공과 복구 가능성, 알림, 디스크·메모리·PID, 시간 동기화를 확인한다. 연구는 새 구간으로 재개하고 이전 자료를 합쳐 성공 시간을 부풀리지 않는다.
6. 재부팅 후 수집·타이머·연구 재개를 확인한다. 검증이 끝나기 전 기존 NCP 서버를 삭제하지 않는다. 종료 결정 뒤에도 원격 원문·백업의 보관 여부를 별도 기록한다.

## 복구 및 비용

- 누락·중복, 큐 증가, 계정 혼선, 반복 종료 또는 백업 실패 시 신규 쓰기를 먼저 중단한다. 새 서버에서 접수된 큐/처리 이력을 보존하고 이전 큐와 비교한 후 이전 서버를 재개한다. 오래된 볼륨을 무조건 재생하면 중복 처리가 생길 수 있다.
- 실제 호스트 장애 복구와 재부팅 검증을 수행하기 전에는 고가용성·무중단을 보증하지 않는다.
- 공급자 신청 요금은 부가세 별도 1,240원/일 또는 33,400원/월이다. 월 중간 이용은 일 요금 조건을 적용하며, 기존 서버와 후보 검증 기간의 비용이 겹친다. 중지 상태도 요금이 발생할 수 있으므로 폐기 후보를 무기한 남기지 않는다. 별도 저장소·백업·트래픽 초과 비용은 포함하지 않는다.
- 공개 기록에는 비밀키, 인증값, 회원 식별자, 원문 로그, 서버 접속 주소와 계정 자료를 넣지 않는다.
